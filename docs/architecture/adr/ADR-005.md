# ADR-005 — Architecture API

- **Numéro** : ADR-005
- **Titre** : Architecture API
- **Statut** : ACCEPTÉE
- **Corpus** : Architecture Horizon v1.0 — GELÉE
- **Référence** : v1.0.1 / d59409b8257f5a725828e281884a1c92e40da7a6
- **Date** : non consignée dans la source
- **Consolidation** : version finale produite à partir du texte initial et des ajustements validés

> **[F]** fait vérifié · **[R]** recommandation · **[H]** hypothèse

## 1. Statut

**ACCEPTÉE.** Dépend des ADR-001 à 004 (acceptées) et des deux cartographies (validées). Bloque les ADR-007, 009, 010 et 015.

## 2. Contexte et problème

Cinq routes existent, **toutes publiques** (`permission_callback => '__return_true'`) **[F]**. Le back-office n'utilise pas l'API : il passe par `admin-post.php` et la capacité WordPress **[F]**. **Il n'existe donc aujourd'hui aucun contrat API réutilisable par un consommateur tiers.**

**Problème à résoudre** : décider les surfaces d'API, leurs contrats, et le sort des cinq routes existantes.

## 3. Principes

1. **Le chemin le moins privilégié qui fonctionne.** Lecture filtrée → RLS. Écriture sans invariant → RLS. Commande → fonction sous JWT utilisateur. Élévation seulement si nécessaire (A15).
2. **Contrats partagés ou spécialisés selon la sémantique** — voir ci-dessous.
3. **Aucune donnée commerciale dans un contrat opérationnel** (⛔1) — contrainte de conception, pas de filtrage.
4. **Toute commande externe est idempotente côté serveur** (A10).
5. **WP REST ne devient jamais un backend mobile** (ADR-001).
6. **Une erreur ne renseigne jamais l'appelant au-delà du nécessaire.**

### 3.1 Contrats partagés et contrats spécialisés

> **« Les contrats métier peuvent être partagés lorsqu'ils portent exactement la même sémantique, les mêmes garanties et le même niveau de confidentialité. Les projections de données et les commandes doivent être spécialisées dès que les populations, les droits, la confidentialité ou les règles d'autorisation diffèrent. »**

| Niveau | Partage | Exemples |
|---|---|---|
| **Types de valeur** | **Partagés** | Identifiant · adresse normalisée · statut · période · pagination · erreur standard |
| **Projections** | **Spécialisées** | Vue CRM interne · vue opérationnelle chauffeur · vue partenaire · vue client |
| **Commandes** | **Spécialisées** par domaine et par niveau d'autorisation | Transition commerciale ≠ transition opérationnelle |

**Principe obligatoire : « La réutilisation d'un schéma ne doit jamais conduire à exposer une donnée supplémentaire simplement parce qu'un autre consommateur en a besoin. »**

Un type de valeur partagé décrit une **forme** ; une projection décrit un **périmètre de confidentialité**. Confondre les deux est précisément le mécanisme par lequel une donnée commerciale finirait dans un contrat opérationnel (⛔1).

## 4. Familles de surfaces

| # | Surface | Auth | Privilège | Rattachement |
|---|---|---|---|---|
| 1 | Routes publiques WordPress | aucune | `service_role` via PHP | Existant **[F]** |
| 2 | Lectures authentifiées PostgREST | JWT | aucun — RLS | Nouveau |

Les huit surfaces se rattachent aux quatre familles d'accès de la Cartographie des flux d'autorisation : anonyme borné (1), JWT sous RLS (2, 4, 8), privilégié (3, 5, 6, 7). **Une neuvième surface qui ne se rattacherait à aucune serait un signal d'alerte architectural.**

## 5. Classification des opérations

| Type | Voie | Idempotence | Attribution |
|---|---|---|---|
| **Lecture** | PostgREST + RLS | — | **Voir §5.1** |
| **Écriture simple** *(sans invariant transversal)* | PostgREST + RLS | Si répétable | Acteur |
| **Commande métier** | Fonction cat. A ; B si justifié | **Obligatoire** | Acteur |
| **Action sensible** | Commande + **acteur humain résolu** | Obligatoire | **Humain, jamais de repli** |
| **Webhook** | Fonction cat. B | **Obligatoire** | Acteur de service |
| **Traitement asynchrone** | Worker | Existante **[F]** | Acteur de service |
| **Opération administrative** | API privée | Obligatoire | **Humain + MFA** |

**Règle de tri** : si une écriture engage un invariant dépassant la ligne écrite, c'est une commande. **La qualification appartient au runtime** (ADR-004 §12 bis), jamais à l'appelant.

### 5.1 Traçabilité des lectures

> **« Toute lecture authentifiée doit être attribuable techniquement. Les lectures sensibles produisent en plus un audit métier explicite. »**

| | **Trace technique** | **Audit métier de lecture** |
|---|---|---|
| Périmètre | **Toute lecture authentifiée** | Lectures sensibles uniquement |
| Contenu | Identifiant de requête · acteur résolu · contexte · origine · ressource ou catégorie consultée · résultat global · durée · **sans PII inutile** | Attribution métier explicite, conservée |
| Volume | **Agrégeable ou échantillonnable** selon le volume, sauf obligation de sécurité contraire | Jamais échantillonné |

**Lectures sensibles** : export · consultation de données personnelles étendues · accès financier · accès administratif transversal · téléchargement de documents sensibles · **accès exceptionnel ou dérogatoire** · consultation dans le cadre d'un incident · accès à une configuration de sécurité.

La classification est faite **par le runtime** (ADR-004 §12 bis), jamais déclarée par l'appelant. La liste définitive relève des ADR-011 et 012.

## 7. API publiques existantes — décisions

| Route | Utilité | Risque constaté **[F]** | Protection actuelle **[F]** | Protection cible | Décision |
|---|---|---|---|---|---|
| `POST /enquiries` | Cœur du parcours public | Abus automatisé | nonce · honeypot · débit · CORS · idempotence | Débit fondé sur une IP fiable ; honeypot **déclassé** comme protection | **Maintenue, durcie** |
| `GET /form-token` | Jeton frais robuste au cache | **Seule route sans limitation de débit ni contrôle d'origine** | aucune | Alignement sur les trois autres | **Maintenue, alignée** |
| `GET /enquiries/{ref}/receipt` | Reçu public | **Énumération** — références séquentielles ; expose trajet, date, passagers, statut | Débit seul | **Jeton non devinable, dissocié de la référence** | **Mode d'accès refondu** |
| `POST /enquiries/{ref}/whatsapp-opened` | Marquer « opened » | Écriture anonyme sur référence arbitraire → **entrée d'audit** | nonce · débit | **Lié au même jeton de possession** | **Modifiée** |
| `GET /health` | Supervision | Expose publiquement version, environnement et état de la base | aucune | **Réponse minimale en public**, détail réservé aux appelants autorisés | **Modifiée** |

**Traitement prioritaire des cinq points signalés :**

**a) Reçu énumérable.** La minimisation actuelle est réelle et volontaire — aucun nom, aucun courriel, aucun téléphone **[F]**. Mais trajet, date et statut sur des références séquentielles suffisent à reconstituer l'activité de la Maison. **La correction n'est pas de retirer des champs : c'est de rendre l'accès non devinable.**

**Point de rigueur** : le commentaire de la méthode annonce « réponse générique (aucun oracle d'existence) », alors que le code renvoie **404 pour une référence inconnue et 200 sinon** **[F]**. **C'est un oracle d'existence, et le commentaire est contredit par son propre code.** La formulation exacte est correcte pour `whatsapp-opened`, qui répond toujours de la même façon **[F]** — pas pour le reçu. La cible doit supprimer l'oracle, pas seulement documenter son absence.

**b) Écriture anonyme.** Aujourd'hui, un jeton librement obtenu suffit à basculer la communication d'une demande tierce et à créer une entrée d'audit **[F]**. Cible : lier l'appel à la preuve de possession du reçu — un même mécanisme résout **a** et **b**.

**c) `form-token` sans garde comparable.** Alignement sur les autres routes. **Réserve** : cela réduit l'abus, sans changer le fait qu'un jeton anonyme WordPress n'authentifie personne. Le durcissement est réel mais borné.

**d) Débit fondé sur l'IP.** `REMOTE_ADDR` seul **[F]**. Derrière un mandataire, soit toutes les requêtes partagent une IP — auto-blocage — soit l'IP réelle n'est jamais vue. **Bloqué par Q1.** Décision intermédiaire : **ne pas ajouter de nouveau contrôle dépendant de l'IP** tant que Q1 n'est pas résolue, et prévoir un axe complémentaire par jeton ou session.

**e) Idempotence existante.** Fonctionnelle, mais stockée en transients WordPress **[F]** : durabilité incertaine sans cache objet persistant (Q1), et **invisible depuis les autres runtimes**. Cible : **idempotence persistée en base**, seule voie compatible avec la synchronisation mobile et les Edge Functions.

### 7.1 `GET /health` — trois notions distinctes

Trois notions, aujourd'hui confondues en une seule réponse publique **[F]** :

| Notion | Contenu | Exposition |
|---|---|---|
| **Liveness** | Le processus répond | **Seule exposition publique éventuelle** — minimale |
| **Readiness** | Les dépendances nécessaires fonctionnent | Réservée |
| **Diagnostic détaillé** | Version, environnement, configuration, état de la base | **Opérateurs uniquement** |

**La surface publique éventuelle n'expose au maximum qu'une liveness minimale — sans version, sans environnement, sans configuration, sans détail de base.** La réponse actuelle expose les quatre **[F]**.

**Q-R reste ouverte** : la liveness doit-elle rester publique, ou tout devenir réservé ?

## 8. API authentifiées

| Consommateur | Lectures | Écritures |
|---|---|---|
| **Espace client** | PostgREST + RLS, relation dédiée | Écritures simples ◐, à confirmer |
| **PWA chauffeur** | PostgREST + RLS, relation **opérationnelle** ⛔ sans commercial | **Commandes uniquement** |
| **Portail partenaire** | Idem, périmètre borné par affectation | **Commandes uniquement** |

**Aucune lecture ne passe par une fonction serveur** lorsque RLS suffit : c'est le principal gain de productivité de l'ADR-001, et il ne doit pas être dilapidé par des points d'entrée intermédiaires inutiles.

**Rappel structurant** : la relation dédiée clarifie le contrat mais **n'est pas la frontière de sécurité** (A8) — celle-ci reste RLS. **Q-N conditionne cette section.**

## 9. Edge Functions

| Type | Catégorie | Justification de l'élévation |
|---|---|---|
| Commande chauffeur / partenaire | **A par défaut** | Élévation seulement si multi-table ou transactionnelle |
| Commande multi-agrégat | B | Cohérence transactionnelle inatteignable sous RLS |
| Webhook | **B** | Aucun JWT utilisateur — l'appelant est un tiers signé |
| Worker planifié | **B** | Aucun utilisateur ; acteur de service |
| Passerelle IA | **Ni A ni B** | **Rôle restreint dédié** — jamais `service_role` |

**Conditions cumulatives d'élévation** (A15) : authentification ou signature vérifiée · acteur ou service résolu · autorisation explicite · action qualifiée · idempotence · audit · **périmètre de la fonction strictement réduit**.

**Chaque élévation est documentée dans l'ADR ou le journal de décision, avec son motif.** Une élévation non justifiée est un défaut, pas un choix.

## 10. API privées administratives

Réservées aux opérations sensibles : gestion des rôles, purge, anonymisation, export, approbation.

**Une origine HTTP et une politique CORS ne constituent pas une frontière d'autorisation.**

**Quatre notions à ne pas confondre :**

| Notion | Signification |
|---|---|
| **Publiquement routable** | L'adresse répond depuis Internet |
| **Authentifié** | Une identité valide est présentée |
| **Autorisé** | Cette identité a le droit de cette opération |
| **Restreint au niveau réseau** | Défense complémentaire, jamais principale |

**Certaines opérations administratives resteront accessibles depuis Internet pour les utilisateurs autorisés, sans être « publiques » pour autant.**

**Exigences** :

- session WordPress valide ;
- **MFA obligatoire** ;
- **acteur humain résolu, refus fermé à défaut** ;
- rôle Horizon adapté ;
- **autorisation vérifiée pour chaque opération** ;
- protection contre la falsification de requête pour les sessions navigateur ;
- idempotence pour les actions à effets multiples ;
- **confirmation renforcée pour les opérations destructives** ;
- journalisation métier ;
- limitation de débit adaptée ;
- restriction réseau **uniquement en défense complémentaire**, si l'hébergement le permet (Q1) ;
- **aucune confiance accordée à la seule origine HTTP**.

## 11. Webhooks

Signature vérifiée · secret dédié par fournisseur et par environnement · anti-rejeu par horodatage et identifiant d'événement · idempotence par identifiant fournisseur — **l'index d'unicité existe déjà** **[F]** · rotation par acceptation temporaire de deux secrets · **jamais d'authentification par IP source ni par obscurité d'URL**.

**Réponse à une répétition : succès idempotent, jamais une erreur** — sinon le fournisseur rejouera indéfiniment.

## 12. Passerelle d'outils IA

Surface unique de l'IA. **Aucun accès direct à la base, jamais de `service_role`** (⛔2, ADR-004 §11 option B).

Contrat : identification de l'agent · résolution de la configuration versionnée · vérification de l'outil dans la liste autorisée · **qualification de l'action par le runtime** · lecture directe ou proposition · **approbation humaine si sensible, revérifiée à l'exécution** · double attribution.

**L'agent ne choisit jamais la qualification, et ne peut pas contourner la classification en changeant d'outil** : elle porte sur l'**effet réel**.

## 13. Versionnement

| Option | Verdict |
|---|---|
| Namespace global versionné | **Écartée** — impose une évolution en bloc de modules aux rythmes différents |
| **Version par module** | **Retenue** |
| **Version par contrat** *(relations dédiées)* | **Retenue, complémentaire** |

**Décisions** : `fcp/v1` est **conservé et stable pour ses contrats compatibles** · chaque nouveau module reçoit son propre espace et sa propre version · un contrat de lecture évolue par **création d'une nouvelle relation**, l'ancienne étant dépréciée puis retirée.

### 13.1 Trois catégories de changement

| Cat. | Nature | Exige une nouvelle version ? | Exemples |
|---|---|---|---|
| **A** | **Durcissement compatible** | **Non**, si le contrat fonctionnel observable reste compatible | Limitation de débit · contrôle d'origine · validation renforcée · réduction du détail de `health` · journalisation · correction d'un comportement abusif non contractuel |
| **B** | **Changement incompatible** | **Oui** — nouvelle version, nouveau point d'entrée, ou période de double fonctionnement | Jeton de possession obligatoire pour le reçu · changement d'URL du reçu · modification de la forme de réponse attendue par le front · suppression de l'accès par la seule référence |
| **C** | **Correction urgente de sécurité** | **Rupture contrôlée admise** | Si le maintien de la compatibilité exposerait les données. **Documentée, annoncée, avec plan de migration** |

> **« `fcp/v1` reste stable pour ses contrats compatibles. Toute modification incompatible est introduite par un contrat versionné ou par une période transitoire explicitement documentée. Une correction urgente de sécurité peut déroger à cette règle avec justification et plan de migration. »**

**Classement des cinq routes existantes :**

| Route | Catégorie |
|---|---|
| `POST /enquiries` — durcissement | **A** |
| `GET /form-token` — alignement | **A** |
| `GET /health` — réduction du détail | **A** |
| `POST /whatsapp-opened` — preuve de possession | **B** |
| `GET /receipt` — refonte du mode d'accès | **B** |

**Plan conceptuel pour le reçu public** *(durées non fixées)* :

1. génération et transmission d'un jeton de possession ;
2. période de double fonctionnement **bornée** ;
3. migration du front et des liens déjà envoyés ;
4. désactivation de l'accès par référence seule ;
5. **vérification qu'aucun oracle d'existence ne subsiste** — y compris dans les codes d'erreur et les délais de réponse.

L'étape 3 est la plus contraignante : des liens déjà envoyés à des clients existent, et leur invalidation doit être anticipée plutôt que subie.

**Compatibilité** : ajout de champ toléré ; retrait ou changement de sens = nouvelle version. **Dépréciation** : annonce, période de double exécution, date de retrait — durée à fixer en ADR-014.

## 14. Pagination, filtrage et limites

L'état actuel est un contre-exemple utile : liste back-office plafonnée à 50 en dur, sans total ni filtre **[F]** ; comptage par statut chargeant **toutes** les lignes pour compter côté PHP **[F]** ; plusieurs lectures sans limite **[F]**.

**Règles** **[R]** :

1. **Toute liste a une limite par défaut et une limite maximale.** Aucune exception.
2. **Aucun agrégat calculé côté application** — les comptages sont faits par la base.
3. Pagination par curseur préférée à la pagination par décalage sur les ensembles appelés à croître.
4. Filtrage et tri sur un **ensemble déclaré** de champs, jamais arbitraires.
5. **Toute lecture sans limite est un défaut**, détectable en revue.

## 15. Idempotence

> **« La clé d'idempotence est créée par l'initiateur fiable de l'intention et reste stable lors de tous les rejeux de cette même intention. »**

**Initiateurs possibles** : PWA · portail partenaire · WordPress · fournisseur de webhook · worker · événement métier · runtime serveur · **parcours public anonyme**.

**Portée : (principal d'idempotence, type de commande, clé)**

| Le principal peut être | Cas |
|---|---|
| Acteur humain | Commande d'un chauffeur, d'un partenaire, d'un client |
| Acteur de service | Worker, tâche planifiée |
| Identifiant fournisseur | Webhook |
| Organisation | Commande engageant l'organisation |
| **Identifiant de corrélation anonyme** | Parcours public — cas actuel du formulaire **[F]** |
| Autre principal technique explicitement reconnu | Cas futur |

**Commandes concernées** : affectation · acceptation · changement d'état · annulation · approbation · paiement · webhook · synchronisation mobile · envoi.

**Exigences :**

1. **Empreinte du contenu** de la commande conservée avec la clé ;
2. même clé + même contenu → **résultat précédent rejoué** ;
3. même clé + contenu différent → **conflit explicite** ;
4. **statut de traitement stocké** (en cours, terminé, échoué) ;
5. **gestion des commandes encore en cours** — une répétition pendant le traitement ne doit ni doubler l'effet ni échouer brutalement ;
6. résultat rejouable **sans reproduire les effets** ;
7. durée de rétention **définie par type d'opération** (Q-P) ;
8. **aucune confiance dans la seule bonne conduite du client** — la garantie est serveur.

L'exigence 5 est celle qui manque le plus souvent : sans statut intermédiaire, deux requêtes concurrentes portant la même clé produisent deux traitements.

**Stockage** : **base**, jamais transients WordPress — durabilité et visibilité inter-runtimes.
**Webhooks** : identifiant fournisseur, index existant **[F]**.

## 16. Erreurs

| Catégorie | Sémantique |
|---|---|
| Validation | Entrée non conforme |
| Non authentifié | Aucune identité valide |
| **Non autorisé** | Identité valide, droit absent |
| Ressource absente | **À manier avec précaution — voir ci-dessous** |
| Conflit | État incompatible ou collision de clé |
| **Commande déjà traitée** | Répétition idempotente — **succès, pas erreur** |
| État invalide | Transition interdite |
| Limitation de débit | Seuil atteint |
| Erreur temporaire | Réessai pertinent |
| Erreur fournisseur | Tiers en échec |
| Erreur interne | Non détaillée |

**Ne jamais exposer** : détail SQL · secret · structure interne · **existence d'une ressource lorsque cela facilite l'énumération**.

**Application directe au reçu public** : la distinction 404 / 200 **[F]** est précisément le cas visé par la dernière clause. La cible doit répondre de façon indistinguable pour une référence inexistante et pour un jeton invalide.

|---|---|---|

## 18. Observabilité

**Champs propagés de bout en bout** : identifiant de requête · identifiant de corrélation · acteur · clé d'idempotence · identifiant d'événement · durée · statut · origine · contexte.

**Amorces existantes** : `audit_logs.request_id` au schéma **[F]**, identifiant généré à chaque création de demande **[F]**, journalisation avec masquage des clés sensibles **[F]**.

**Règles** : aucune donnée personnelle inutile en journal · le masquage actuel repose sur le **nom** de la clé, ce que le code documente honnêtement **[F]** — une valeur sensible sous un nom non répertorié ne serait pas masquée, donc les contrats doivent éviter de véhiculer des secrets sous des noms libres · **la journalisation technique ne bloque jamais l'opération métier** (A16).

## 19. Invariants

**Aucun invariant numéroté n'est créé par l'ADR-005.**

La présente ADR **applique** des invariants formulés dans la Cartographie des flux d'autorisation, notamment : **A5** (action sensible ⇒ acteur humain résolu), **A7** (`service_role` confiné), **A8** (une relation dédiée n'est pas une frontière de sécurité), **A9** (résolution dynamique obligatoire), **A10** (commande externe à effets multiples idempotente), **A15** (fonction privilégiée : revalider, résoudre, autoriser, limiter), **A16** (cohérence état / événement / attribution ; logs hors transaction), ainsi que les interdictions **⛔1** (aucune donnée commerciale pour chauffeur et partenaire) et **⛔2** (aucun accès d'un agent à sa configuration).

## 20. Conséquences positives

Les lectures externes ne coûtent aucun code serveur · les cinq routes existantes sont conservées et durcies, non réécrites · un même mécanisme de possession résout l'énumération du reçu et l'écriture anonyme · l'idempotence en base sert simultanément le mobile, les webhooks et les Edge Functions · le versionnement par module évite l'évolution en bloc · la catégorie A limite le recours à `service_role` · deux mécanismes existent déjà et sont réutilisés **[F]**.

## 21. Conséquences négatives

Le reçu public change de mode d'accès — impact sur le parcours client existant · l'idempotence quitte les transients pour la base, ce qui est une modification d'un comportement en production · davantage de contrats à maintenir (un par consommateur) · la limitation de débit reste imparfaite tant que Q1 n'est pas résolue · le versionnement par module exige une discipline de dépréciation qui n'existe pas encore.

## 22. Risques

| Risque | Gravité | Atténuation |
|---|---|---|
| Élévation injustifiée en catégorie B | **Critique** | A15, justification documentée, revue |
| Fuite commerciale par un contrat opérationnel | **Critique** | Cloisonnement par conception ; tests négatifs |
| Relation dédiée n'appliquant pas les policies | **Critique** | **Q-N, bloquante** |
| Idempotence non couvrante → double effet | Élevée | Portée par principal, collision en conflit, audit des répétitions |
| Message d'erreur révélant une existence | Élevée | Taxonomie §16, tests d'énumération |
| Débit inopérant derrière un mandataire | Élevée | **Q1** ; pas de nouveau contrôle dépendant de l'IP entre-temps |
| Rupture du parcours client au changement du reçu | Moyenne | Période de double fonctionnement |

## 23. Réversibilité

| Décision | Retour arrière | Coût |
|---|---|---|
| Durcissement de `form-token` | Retrait des gardes | nul |
| Alignement CORS | Retrait | nul |
| Idempotence en base | Retour aux transients | faible |
| Réponse minimale de `health` | Restauration | nul |
| Catégorie A par défaut | Élévation ponctuelle | faible |
| Versionnement par module | Regroupement ultérieur | faible |
| **Refonte du mode d'accès au reçu** | **Modifie un parcours en production** | **moyen** |
| Contrats par consommateur | Fusion ultérieure | moyen |

**Un seul point à impact utilisateur** : le reçu public. Il justifie une période de double fonctionnement plutôt qu'une bascule sèche.

## 25. Conditions d'acceptation

1. Les **huit surfaces** sont validées, rattachées aux quatre familles d'accès ; une neuvième vaudrait signal d'alerte.
2. Le principe du **chemin le moins privilégié** est validé, avec la catégorie A par défaut et l'élévation documentée cas par cas.
3. *(2 bis)* Les contrats sont **partagés au niveau des types de valeur, spécialisés au niveau des projections et des commandes**, sans jamais exposer une donnée supplémentaire par réutilisation.
4. Les **décisions sur les cinq routes existantes** sont validées : `enquiries` durcie · `form-token` alignée · **reçu refondu dans son mode d'accès** · `whatsapp-opened` liée à une preuve de possession · `health` réduite en public.
5. Il est acté que **le reçu constitue aujourd'hui un oracle d'existence**, contrairement à ce qu'affirme le commentaire du code **[F]**, et que la cible supprime l'oracle.
6. **L'idempotence migre des transients vers la base**, avec portée **(principal, type, clé)**, empreinte de contenu, statut de traitement, gestion des commandes en cours, et **conflit explicite en cas de collision**.
7. **Aucun nouveau contrôle dépendant de l'IP** n'est introduit tant que Q1 n'est pas résolue.
8. Le **versionnement par module et par contrat** est retenu, avec les **trois catégories A / B / C** ; `fcp/v1` reste stable pour ses contrats compatibles ; les routes reçu et `whatsapp-opened` relèvent de la catégorie B avec période de double fonctionnement.
9. Les cinq règles de pagination et de limites sont validées, **toute lecture sans limite étant un défaut**.
10. La taxonomie d'erreurs est validée, **une répétition idempotente étant un succès et non une erreur**.
11. Le **cloisonnement commercial est obtenu par conception des contrats**, jamais par filtrage applicatif.
12. **Toute lecture authentifiée est attribuable techniquement ; les lectures sensibles produisent un audit métier explicite.**
13. Les **API administratives** reposent sur authentification, MFA, acteur humain, autorisation par opération et protection contre la falsification de requête — **jamais sur l'origine HTTP** ; la restriction réseau n'est qu'une défense complémentaire.
14. **`health` sépare liveness, readiness et diagnostic** ; l'exposition publique éventuelle se limite à une liveness minimale.
15. **Q-N reste bloquante pour le §8** ; Q-P, Q-Q et Q-R sont renvoyées aux ADR-010, 011 et 012.

# ADR-015 — Qualité, tests et gouvernance CI/CD

- **Numéro** : ADR-015

- **Statut** : ACCEPTÉE
- **Corpus** : Architecture Horizon v1.0 — GELÉE
- **Référence** : v1.0.1 / d59409b8257f5a725828e281884a1c92e40da7a6
- **Date** : non consignée dans la source
- **Consolidation** : version finale produite à partir du texte initial, validé dans son fond sans ajustement architectural

## 1. Statut

**ACCEPTÉE.** Dépend des ADR-001 à 014. **Clôt le corpus architectural.**

Elle est la seule ADR **applicable immédiatement, sans attendre aucune autre** — et la seule dont l'absence rend toutes les autres invérifiables.

### 1.1 Contexte

*Section structurelle. Le contenu est dérivé des §2, §3, §4, §10, §12 et §13 ; aucune décision nouvelle n'y est introduite.*

| Fait vérifié | Conséquence |
|---|---|
| L'installation des dépendances **tolère son propre échec**, et l'exécution des tests est conditionnée à la présence du binaire **[F]** | Un échec d'installation produit une **construction verte avec zéro test exécuté** |
| **Aucun verrou de dépendances** **[F]** | Chaque exécution est non reproductible |
| La chaîne mesure `coverage: none` **[F]** | **La couverture n'est pas mesurée du tout**, alors que la configuration cible le domaine |
| Seule la convention de nommage des migrations est vérifiée **[F]** | Ni exécution, ni idempotence, ni RLS, ni compatibilité de retour arrière |
| Un fichier de documentation annonce des classes qui n'existent pas, un autre référence des composants supprimés **[F]** | **La dérive documentaire est un mode de défaillance observé**, pas théorique |

Trois niveaux de test n'existent pas : **autorisation, API, exploitation** — exactement ceux qui portent le risque introduit par ce programme.

### 1.2 Énoncé du problème

*Section structurelle. Le contenu est dérivé des §2 à §14 ; aucune décision nouvelle n'y est introduite.*

| Question posée | Formulation |
|---|---|
| Confiance | Que prouve réellement une chaîne verte ? |
| Niveaux | Quels niveaux de test manquent, et pourquoi sont-ce précisément les plus critiques ? |
| Mesure | Que mesure-t-on quand un pourcentage n'a pas de sens ? |
| Autorisation | Comment tester ce qui doit **refuser**, et non ce qui doit fonctionner ? |
| Exploitation | Ce qui ne peut pas s'exécuter dans une chaîne — restauration, rotation — comment le prouve-t-on ? |
| Documentation | Comment détecter une documentation devenue fausse ? |
| Livraison | Qu'est-ce qui est **vérifiable** avant une mise en production ? |

## 2. Le défaut fondateur

**Une intégration continue verte ne prouve pas aujourd'hui que les tests ont été exécutés.** **[F]**

L'installation des dépendances tolère son propre échec, et l'exécution des tests est conditionnée à la présence du binaire **[F]**. Un échec d'installation produit donc une **construction verte avec zéro test exécuté**. S'y ajoute l'absence de verrou de dépendances **[F]**, qui rend chaque exécution non reproductible.

**Principe fondateur** **[R]** :

> **Aucune étape ne peut absorber son propre échec. L'absence d'exécution d'un test est un échec, jamais une omission.**

Tout le reste de cette ADR en découle. Une chaîne qui ment est pire qu'une chaîne absente : elle produit une confiance imméritée.

## 3. Stratégie de tests

| Niveau | Cible | Environnement | État |
|---|---|---|---|
| **Domaine pur** | Logique métier | PHP seul | **Existe** **[F]** |
| **Contrats** | Interfaces, outils, façades | Doubles | Partiel **[F]** |
| **Intégration applicative** | Orchestration | Doubles en mémoire **[F]** | **Existe** |
| **Autorisation** | **RLS, policies** | **PostgreSQL réel** | **N'existe pas** |
| **API** | Routes, contrats, erreurs | WordPress réel ou harnais | **N'existe pas** **[F]** |
| **Exploitation** | Migrations, restauration, garde-fous | Staging | **N'existe pas** |

**Les trois niveaux manquants sont exactement ceux qui portent le risque introduit par ce programme** : l'autorisation devient la frontière de sécurité, l'API devient un contrat pour des tiers, l'exploitation devient critique avec l'Application Chauffeur.

## 4. Couverture attendue

**La couverture est un indicateur, jamais un objectif.** Le plan initial le disait déjà justement : environ 70 % sur la logique métier critique, **pas uniformément** **[F]**. Cette position est conservée.

**État actuel** **[F]** : la configuration cible le domaine seul, mais la chaîne mesure `coverage: none` — **la couverture n'est donc pas mesurée du tout**.

| Périmètre | Métrique pertinente |
|---|---|
| Domaine | Couverture de lignes — élevée, peu coûteuse |
| **Autorisation** | **Complétude des cas négatifs, pas un pourcentage** |
| API | Chaque route × chaque classe d'erreur |
| Outils IA | Chaque outil × validation, autorisation, effet, audit |

**Pour l'autorisation, la métrique utile est : chaque population × chaque catégorie de donnée possède un test négatif.** La matrice de la cartographie fournit directement ce plan de test. **Un jeu de policies couvert à 100 % sans test négatif ne prouve rien** — il prouve que le code s'exécute, pas qu'il refuse.

## 5. Tests d'autorisation et RLS

**Exigence structurante : une base PostgreSQL réelle dans la chaîne.** Les doubles en mémoire actuels **[F]** sont parfaitement adaptés au domaine et **totalement inadaptés à RLS** — ils ne l'exécutent pas.

| Test | Vérifie |
|---|---|
| Positif par policy | L'accès prévu fonctionne |
| **Négatif par population** | **Ce qui est interdit l'est réellement** |
| Acteur désactivé | Refus sur toutes les surfaces (I6) |
| Contexte | Un jeton chauffeur n'ouvre **aucune** donnée commerciale (⛔1) |
| Affectation | Aucun accès avant, aucun après clôture |
| Délai de grâce | Lecture seule, aucune commande |
| Fonctions de policy | Testées isolément, chemin de recherche figé |
| **Vue dédiée** | Comportement réel vis-à-vis de RLS — **Q-N** |

**Deux règles bloquantes** **[R]** :

- **Une table avec RLS activée et sans test de policy fait échouer la construction.** C'est la traduction mécanique de la règle 5 de l'ADR-004 §13.
- **Un test de refus qui cesse d'échouer est une alerte de sécurité**, traitée comme une régression bloquante.

## 6. Tests d'API

Par route : succès · erreur de validation · non authentifié · **non autorisé** · ressource absente · limitation de débit · **rejeu idempotent**.

**Trois tests dérivés directement de défauts vérifiés :**

| Test | Défaut visé **[F]** |
|---|---|
| **Indistinguabilité** : référence inconnue et jeton invalide produisent une réponse identique | Le reçu renvoie **404 contre 200** — oracle d'existence |
| **`form-token` soumis aux mêmes gardes** que les autres routes | Seule route sans limitation de débit ni contrôle d'origine |
| **`health` public n'expose ni version, ni environnement, ni état de base** | Les quatre sont exposés aujourd'hui |

Idempotence : même clé + même contenu ⇒ même résultat · même clé + contenu différent ⇒ **conflit** · commande en cours ⇒ ni doublon ni échec brutal.

## 7. Tests des Edge Functions

| Catégorie | Tests |
|---|---|
| **A — sous JWT utilisateur** | RLS s'applique réellement · aucun accès hors périmètre de l'utilisateur |
| **B — privilégiée** | **Revalide l'identité · résout l'acteur · qualifie l'action · applique l'idempotence · limite son périmètre** (A15) |
| **B — acteur désactivé** | **Refus** — c'est la garantie que le contournement de RLS n'ouvre pas tout |
| Webhook | Signature invalide ⇒ refus · rejeu ⇒ succès idempotent · horodatage hors fenêtre ⇒ refus |

Le troisième test est le plus important : une fonction privilégiée qui n'appliquerait pas A15 serait un contournement complet du dispositif d'autorisation.

## 8. Tests des drapeaux

| Test | Invariant |
|---|---|
| Drapeau absent ou illisible ⇒ **désactivé** | Défaut sûr |
| Drapeau éteint ⇒ fonctionnalité **absente**, non « présente mais interdite » | **E8** |
| **Drapeau allumé sans autorisation ⇒ refus** | **E8 — le test décisif** |
| État par environnement | DPL4 |

Le troisième prouve qu'un drapeau n'est pas devenu un mécanisme d'autorisation par inadvertance — c'est le risque exact que **E8** vise.

## 9. Tests des agents IA

**Exécutables sans modèle** (**IA3**). Ce qui est non déterministe — le choix du modèle d'appeler tel outil — n'est jamais ce qui garantit la sécurité.

| Test | Invariant |
|---|---|
| Outil : validation, autorisation, effet, audit | **IA3** |
| Agent suspendu refusé **à la proposition ET à l'exécution** | ADR-003 §11 |
| Outil hors liste ⇒ refus **et entrée au journal de sécurité** | ADR-012 §2 |
| **Deux outils au même effet ⇒ même qualification** | ADR-004 §12 |
| **Agent ne peut ni lire ni écrire sa configuration** | **A14** |
| Approbateur sans droit propre ⇒ refus | **R1** |
| Approbation expirée ⇒ nouvelle proposition requise | R3 |
| Rôle de base restreint ⇒ RLS s'applique à l'IA | ADR-004 §11 |

## 10. Tests de migration

**État actuel** **[F]** : seule la convention de nommage est vérifiée.

| Test | Vérifie |
|---|---|
| **Exécution réelle sur base vide** | Ordre et dépendances |
| **Idempotence** | La stratégie actuelle en dépend entièrement **[F]** |
| Amorçage | Les cinq migrations existantes sont **enregistrées sans être rejouées** **[F]** |
| Empreinte divergente | **Bloque** (invariant **D6** de l'ADR-010) |
| **RLS dans la migration de création** | ADR-004 §13 |
| **Compatibilité de retour arrière** | **La suite de tests de la livraison précédente passe sur le nouveau schéma** |

Le dernier test est la vérification mécanique de la règle « le code doit toujours pouvoir revenir en arrière » (ADR-014 §5). Sans lui, cette règle reste déclarative.

## 11. Tests de restauration et exercices

**Distinction importante** **[R]** :

| | **Test d'intégration continue** | **Exercice périodique** |
|---|---|---|
| Fréquence | Chaque livraison | Calendrier (**CT4**) |
| Exemples | Domaine, autorisation, API, migrations | **Restauration · rotation · perte de runtime · indisponibilité fournisseur** |
| Effet sur la production | Bloque la livraison | **La fraîcheur du dernier exercice réussi est un critère de livraison** |

**Une restauration ne se teste pas dans une chaîne d'intégration** — elle s'éprouve en staging, et c'est **la date de son dernier succès** (**CT3**) qui devient opposable avant une mise en production.

## 12. Qualité documentaire

**La dérive documentaire est un mode de défaillance observé, pas théorique** **[F]** : un fichier de documentation annonce des classes qui n'existent pas, un autre référence des composants supprimés.

**Contrôles automatisables** : référence d'ADR inexistante · lien interne rompu · **contrat déclaré Stable sans suite de tests** (G2) · **hook déclaré de niveau 3 sans documentation** (G4) · **procédure sans date de dernière exécution réussie** (**CT3**) · **drapeau temporaire au-delà de sa date sans justification** (DPL2).

**Règle rappelée** : un contrat non documenté n'est pas un contrat (ADR-006).

## 13. Gouvernance CI/CD

**Neuf étapes, toutes bloquantes, aucune conditionnelle.**

| # | Étape | Corrige |
|---|---|---|
| 1 | **Reproductibilité** — verrou versionné, installation qui doit réussir | **défauts D1 et D2 de l'audit** **[F]** |
| 2 | **Analyse statique** — syntaxe **[F]**, style PHP avec sa configuration et son greffon d'enregistrement, lint JS et CSS | **défauts D3, D4 et D6 de l'audit** **[F]** |
| 3 | Unitaires et intégration sur doubles | Existe **[F]** |
| 4 | **Autorisation sur PostgreSQL réel** | **Nouveau — le plus structurant** |
| 5 | **Contrats d'API** | **défaut D5 de l'audit** **[F]** |
| 6 | **Migrations** — exécution, idempotence, RLS, compatibilité arrière | **[F]** |
| 7 | **Sécurité** — secrets **[F]**, audit de dépendances, **zones interdites aux hooks** | Nouveau |
| 8 | **Cohérence** — en-tête de plugin contre constante, versions déclarées | **[F]** |
| 9 | **Couverture mesurée et publiée** | **[F]** |

> **Avertissement de lecture** : les identifiants **D1 à D6** de la colonne « Corrige » désignent les **défauts relevés par l'audit technique global**, et **non** les invariants **D1 à D6** de la famille *Données* de l'ADR-010. Les deux séries portent les mêmes symboles sans aucun rapport entre elles. Cette collision de symboles est signalée, non résolue : elle appelle une décision documentaire distincte.

**Matrice de versions PHP** : la version réellement exécutée en production est inconnue **[F]** et la chaîne n'en teste qu'une. **Mesure intermédiaire** : tester la version minimale déclarée et la plus récente supportée, jusqu'à ce que **Q-AK** tranche.

**Règle transversale** : **aucune étape n'est conditionnée au succès d'une étape optionnelle antérieure.** C'est la mécanique exacte du défaut actuel **[F]**.

## 14. Obligations avant toute mise en production

**Douze obligations, toutes vérifiables.**

| # | Obligation | Origine |
|---|---|---|
| 1 | **La chaîne est verte ET prouve que les tests ont été exécutés** | §2 |
| 2 | Tests d'autorisation présents pour toute table touchée | §5 |
| 3 | **Garde-fou d'environnement vérifié** | **E9** |
| 4 | Migrations appliquées en staging, registre cohérent | D6 *(ADR-010)* |
| 5 | Recette staging conforme | **[F]** |
| 6 | **Manifeste de livraison complet** | **DPL1** |
| 7 | **Identifiant de déploiement attribué** | DPL3 |
| 8 | **Procédure de retour arrière applicable et identifiée** | DPL5 |
| 9 | Drapeaux dans l'état attendu, avec type et date de retrait | DPL2 |
| 10 | **Exercice de restauration récent** | **CT4**, **CT3** |
| 11 | **Procédure de rotation exécutée au moins une fois** | ADR-013 §7 |
| 12 | **Accord explicite du responsable de validation** | **Déjà en vigueur** **[F]** |

Les obligations 10 et 11 sont aujourd'hui **impossibles à satisfaire** : ni restauration ni rotation n'ont jamais été exécutées **[F]**. C'est la raison pour laquelle elles figurent ici.

## 16. Responsabilités

*Section structurelle. La répartition est dérivée des §2 à §14 ; aucune responsabilité nouvelle n'est créée.*

| Acteur ou composant | Responsable de | Jamais responsable de |
|---|---|---|
| **Chaîne d'intégration continue** | Prouver que les tests ont été exécutés · les neuf étapes bloquantes du §13 · publier la couverture | **Absorber son propre échec** (§2) · conditionner une étape au succès d'une étape optionnelle |
| **Tests d'autorisation** | Démontrer ce qui est **refusé**, sur PostgreSQL réel | Se satisfaire d'un pourcentage (§4) |
| **Tests d'API** | Chaque route × chaque classe d'erreur · l'indistinguabilité · le rejeu idempotent | Laisser subsister un oracle d'existence **[F]** |
| **Tests d'IA** | Valider outil par outil, sans modèle (**IA3**) | Dépendre d'un fournisseur de modèle |
| **Tests de migration** | Exécution, idempotence, amorçage, RLS, **compatibilité de retour arrière** | Se limiter à la convention de nommage **[F]** |
| **Exercices périodiques** | Restauration, rotation, perte de runtime, indisponibilité fournisseur (**CT4**) | Être exécutés dans une chaîne d'intégration (§11) |
| **Contrôles documentaires** | Détecter la dérive : ADR inexistante, lien rompu, contrat Stable sans tests, procédure sans date | — |

## 18. Conséquences positives

Le défaut fondateur est corrigé, et avec lui la valeur de tout le corpus · la matrice d'autorisation devient directement un plan de test · trois tests d'API dérivent de défauts vérifiés · les tests d'IA s'exécutent sans modèle · la compatibilité de retour arrière devient mécanique · la qualité documentaire devient contrôlable, la dérive étant un défaut observé **[F]**.

## 19. Conséquences négatives

Une base PostgreSQL réelle alourdit et ralentit la chaîne · neuf étapes bloquantes augmentent les faux blocages initiaux · deux obligations ne sont pas satisfaisables aujourd'hui · la matrice de versions reste incomplète tant que Q-AK n'est pas tranchée · les exercices périodiques sont un travail récurrent.

## 20. Risques

| Risque | Gravité | Atténuation |
|---|---|---|
| **La chaîne reste complaisante** | **Critique** | §2 — aucune étape n'absorbe son échec |
| Test de refus cessant d'échouer, non détecté | **Critique** | §5 — traité comme régression bloquante |
| Policy livrée sans test | **Critique** | §5 — échec de construction |
| Tests longs contournés par habitude | Élevée | Séparer rapide et lent, aucun n'étant optionnel |
| Couverture prise pour un objectif | Moyenne | §4 — indicateur, jamais cible |
| Obligations 10 et 11 durablement insatisfaites | Élevée | Les exécuter une première fois, en priorité |

## 21. Réversibilité

Chaque étape est retirable ; aucune décision irréversible. **La seule chose non réversible est la confiance accordée à une chaîne qui mentait** : les livraisons passées ne peuvent pas être revérifiées rétroactivement.

## 23. Conditions d'acceptation

1. **Le principe fondateur est acté** : aucune étape n'absorbe son échec ; l'absence d'exécution d'un test est un échec.
2. Les **six niveaux de test** sont validés, les trois manquants étant ceux qui portent le risque nouveau.
3. **La couverture est un indicateur, jamais un objectif** ; pour l'autorisation, la métrique est la **complétude des cas négatifs**.
4. **Une base PostgreSQL réelle est requise** dans la chaîne ; une table avec RLS et sans test de policy **fait échouer la construction**.
5. **Un test de refus qui cesse d'échouer est une régression bloquante.**
6. Les **trois tests d'API dérivés de défauts vérifiés** sont validés **[F]**.
7. **A15 est testé** : une fonction privilégiée refuse un acteur désactivé.
8. **E8 est testé** : un drapeau allumé sans autorisation ne donne aucun accès.
9. **Les tests d'IA s'exécutent sans modèle** (**IA3**), y compris A14, R1 et R3.
10. **La compatibilité de retour arrière est testée** en exécutant la suite précédente sur le nouveau schéma.
11. **Tests continus et exercices périodiques sont distingués** ; la fraîcheur du dernier exercice réussi est un critère de livraison.
12. Les **neuf étapes bloquantes** et les **douze obligations** sont validées, **10 et 11 étant aujourd'hui insatisfaisables** **[F]**.

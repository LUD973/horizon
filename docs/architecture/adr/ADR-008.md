## 1. Statut

**ACCEPTÉE.** Dépend des ADR-001 à 007 (acceptées). Tranche **Q-V**. Bloque l'Application Chauffeur. C'est l'ADR la plus dépendante de **Q1**.

## 2. Contexte, problème et faits établis

| Fait vérifié | Référence |
|---|---|
| Tout l'asynchrone dépend de WP-Cron : planification à 5 minutes, réveil immédiat après création de demande, purge quotidienne | **[F]** |
| WP-Cron ne se déclenche qu'au trafic — sur un site premium à faible volume, un accusé de réception peut attendre | **[F]** |
| Aucune documentation ne traite d'un ordonnanceur système ou de la désactivation de WP-Cron | **[F]** |
| **Débit de la file : 20 éléments toutes les 300 s, soit un plafond de 240 par heure** | **[F]** |
| Staging et production sont deux projets Supabase distincts | **[F]** |
| **`isProduction()` n'est jamais appelé ; `FCP_ENV` n'est lu que pour être affiché dans `/health`** | **[F]** |
| Q1 — capacités d'ordonnancement de l'hébergement — non déterminée | — |

**Problème à résoudre** : où s'exécute chaque traitement, et comment garantir qu'un traitement critique ne dépende pas du seul trafic WordPress ?

## 3. Responsabilités par runtime

| Runtime | Détient | Ne détient jamais |
|---|---|---|
| **PostgreSQL** | Intégrité · RLS · **émission transactionnelle** (E1) · agrégats et comptages · maintenance purement base | Orchestration · appel externe · décision métier |
| **WordPress / PHP** | Site public · formulaire · back-office · **orchestration du domaine commercial** · commandes dont le consommateur est WordPress | Backend mobile · frontière de sécurité externe · **ordonnanceur fiable pour le temps-sensible** |
| **Edge Functions** | Commandes des consommateurs externes (cat. A par défaut) · webhooks signés · passerelle IA · planification indépendante du trafic | Second exemplaire du domaine commercial |
| **Workers** | **Livraison des événements** · traitement de la file de sortie | Toute décision métier — ils exécutent des handlers |

**Le worker n'est pas un runtime : c'est un rôle**, hébergeable dans WordPress ou dans une Edge Function selon le handler.

### 3.1 Workers sans état

> **« Un worker est totalement remplaçable. »**

Il ne conserve jamais : état métier · session durable · mémoire locale nécessaire à la reprise · progression implicite.

Toute reprise après incident repose **exclusivement** sur PostgreSQL : réservation atomique · journal d'événements · tables de livraison.

**Conséquence** : tout worker peut être arrêté, remplacé, dupliqué ou déplacé sans perte de cohérence. C'est ce qui rend possibles à la fois la coexistence WordPress / Edge Functions (§4) et la parallélisation comme troisième levier de débit (§8).

**Invariant E7.**

## 4. Options étudiées et décision — Q-V : où vit le worker d'événements ?

### 4.1 Options

| Option | Verdict |
|---|---|
| Worker unique dans WordPress | **Insuffisante à terme** — dépend du trafic, inadaptée au temps-sensible |
| Worker unique en Edge Function | **Prématurée** — aucun critère C1–C4 rempli au démarrage |
| **Rôle assigné par handler, hébergement variable** | **Retenue** |

### 4.2 Décision

**Le rôle de worker est assigné par handler, non fixé globalement.** **[R]**

| Phase | Hôte | Justification |
|---|---|---|
| **1 — maintenant** | **WordPress**, comme aujourd'hui **[F]** | Aucun critère d'élévation rempli ; le consommateur est WordPress |
| **2 — Application Chauffeur** | **Edge Function planifiée** pour les handlers temps-sensibles | Critère C4 de l'ADR-001 rempli |
| Durable | **Les deux coexistent**, chacun servant ses handlers | — |

**Propriété qui rend cette migration sûre** : la réservation atomique déjà en place **[F]** garantit qu'un même élément ne peut être traité deux fois, **même si deux workers tournent simultanément**. La bascule d'un handler de WordPress vers une Edge Function peut donc se faire **progressivement, les deux workers actifs, sans risque de double effet**.

C'est une réversibilité rare et concrète : elle découle d'une décision de conception prise au Sprint 1, avant que le besoin n'existe.

### 4.3 Garanties identiques quel que soit le worker

Les garanties suivantes sont **indépendantes du runtime d'exécution** : réservation atomique · idempotence · audit · corrélation · réessais · réconciliation · observabilité.

**Le déplacement d'un handler entre WordPress et une Edge Function ne modifie jamais son comportement métier. Seul change le lieu d'exécution.**

C'est la condition qui rend la migration du §4.2 véritablement sûre : sans cette propriété, déplacer un handler serait un changement fonctionnel déguisé en changement d'exploitation.

**Invariant E10.**

## 5. Planification — comparatif

| Option | Fiabilité | Indépendante du trafic | Appel externe possible | Verdict |
|---|---|---|---|---|
| **WP-Cron seul** | Faible | **Non** **[F]** | Oui | **Insuffisant — état actuel** |
| **Cron système + désactivation de WP-Cron** | Bonne | Oui | Oui | **Retenu, étape 1 — sous réserve de Q1** |
| **`pg_cron`** | Bonne | Oui | **Non** *(et interdit — E1, E6)* | **Retenu pour la maintenance purement base** |
| **Edge Function planifiée** | Bonne | Oui | Oui | **Retenu dès que C4 est rempli** |
| Worker permanent dédié | Très bonne | Oui | Oui | **Écarté** — surdimensionné à Q6 |
| File externe managée | Très bonne | Oui | Oui | **Écarté** — principe 7 |

**Répartition cible** **[R]** :

- **Maintenance purement base** → `pg_cron`. Premier candidat évident : la purge des adresses IP, aujourd'hui planifiée par WP-Cron et déclenchée depuis PHP **[F]**, alors qu'elle est **entièrement en base** et n'a rien à voir avec WordPress.
- **Traitement de la file et livraison d'événements** → cron système appelant WordPress en phase 1, Edge Function planifiée en phase 2.
- **Réveil immédiat après une action** → conservé tel quel **[F]**, comme optimisation de latence — jamais comme garantie.

**Ce dernier point est important** : le réveil immédiat améliore le délai perçu, il ne garantit rien. La garantie vient de l'ordonnanceur périodique.

**Aucune de ces voies n'est présumée disponible** : le choix entre cron système et repli (§6) dépend entièrement de **Q1**, non levée.

### 5.1 Frontière stricte de `pg_cron`

> **« `pg_cron` est réservé aux traitements purement base de données. Il ne planifie jamais une commande métier. »**

| **Autorisé** | **Interdit** |
|---|---|
| Purge · archivage | **Création d'une mission** |
| Statistiques · maintenance | **Changement métier** · **décision métier** |
| Nettoyage | **Appel HTTP** · **réveil d'un runtime** |
| Contrôles techniques SQL | **Orchestration** · **communication** |

Cette frontière prolonge exactement celle des déclencheurs (E1) : la base garantit l'intégrité et exécute sa propre maintenance ; elle n'arbitre ni n'orchestre jamais.

**Conséquence sur la voie de repli du §6** : le réveil de WordPress par une planification Supabase **n'est pas assuré par `pg_cron`** — c'est une fonction planifiée, runtime applicatif, qui l'assure. La distinction n'est pas formelle : elle maintient la base hors de tout rôle d'orchestrateur.

**Invariant E6.**

## 6. Q1 — correction d'une évaluation antérieure

Q1 avait été qualifiée de **bloquante pour l'Application Chauffeur**. C'est **inexact**, et la présente ADR le corrige.

Q1 bloque la **solution la plus simple** (cron système), pas la capacité elle-même. Un repli existe et ne dépend d'aucune capacité de l'hébergeur :

> **Une fonction planifiée côté Supabase peut réveiller WordPress**, en inversant le sens de l'appel. L'ordonnanceur devient alors extérieur à l'hébergement, qui n'a plus qu'à répondre à une requête HTTP authentifiée.

| Cas | Solution |
|---|---|
| L'hébergement offre un cron système | **Cron système** — le plus simple, le moins couplé |
| L'hébergement n'en offre pas | **Planification Supabase réveillant WordPress**, point d'entrée authentifié et à débit limité |

**Q1 reste nécessaire** — elle détermine laquelle des deux voies est retenue, ainsi que les étapes 4 et 5 du protocole de rotation (ADR-003 §9.1) et la fiabilité des transients. **Mais elle ne bloque plus l'Application Chauffeur.**

**Aucune des deux voies n'est présumée disponible tant que Q1 n'est pas levée.**

## 7. Exécution des commandes — synchrone et asynchrone

| Consommateur | Runtime | Élévation |
|---|---|---|
| WordPress | Orchestration PHP | *(sans objet)* |
| Externe | **Edge Function catégorie A par défaut** | Catégorie B seulement si multi-table ou transactionnelle (A15) |
| Webhook | Catégorie B | L'appelant est un tiers signé |

**Règle sur la durée** **[R]** : **aucune commande longue n'est synchrone.** Une commande dont le traitement peut dépasser le budget de la requête est scindée — la commande **accepte**, émet un événement, et le handler fait le travail. Le client est notifié ou interroge l'état.

Le budget de requête PHP réel relève de Q1 ; en son absence, une marge prudente s'impose.

## 8. Répartition des charges et montée en charge

À l'échelle de Q6, la question n'est pas de dimensionner : c'est de **lever quatre limites connues, toutes chiffrables**.

| Limite | Mesure actuelle **[F]** | Levier |
|---|---|---|
| **Débit de la file** | **240 par heure** *(20 × 12)* | Quatre leviers ci-dessous |
| Dépendance au trafic | WP-Cron | §5 |
| Lectures non bornées | Comptage chargeant toutes les lignes | Agrégat calculé en base |
| Transients sans cache persistant | Débit et idempotence | Q1 ; idempotence en base (ADR-005) |

**Ordre des leviers sur le débit**, du moins au plus coûteux :

1. **augmenter la taille du lot** ;
2. **augmenter la fréquence** ;
3. **paralléliser les workers** — sûr grâce à la réservation atomique **[F]** et à E7 ;
4. changer de runtime d'exécution.

**Quatre leviers avant tout changement d'architecture.** Mise en perspective : à quelques centaines de missions par jour avec quelques messages chacune, on reste très en deçà de 240 par heure en régime moyen. Le plafond ne devient sensible qu'en **rafale** — et c'est alors le levier 1 ou 2 qui répond, pas une refonte.

**Concurrence et verrouillage** : la réservation atomique est le seul mécanisme d'exclusion. Aucun verrou applicatif n'est introduit ; deux workers concurrents sont sûrs par construction.

## 9. Supervision

Indicateurs de l'ADR-007 §16, plus **un signal que rien d'autre ne remplace** :

> **Un battement de l'ordonnanceur est obligatoire**, et son absence doit alerter.

C'est le seul défaut qui ne produit aucune erreur : si l'ordonnanceur s'arrête, rien n'échoue — la file grossit simplement, en silence, jusqu'à ce qu'un client s'étonne de n'avoir rien reçu. **L'âge du plus ancien élément en attente et la date de la dernière exécution réussie sont les deux mesures les plus révélatrices du système.**

**Attribution** : tout traitement asynchrone est attribué à un **acteur de service dédié** (I14, A13) — jamais à un acteur générique, jamais à `NULL` (I17).

## 10. Tolérance aux pannes

| Panne | Effet | Comportement attendu |
|---|---|---|
| **Supabase indisponible** | Tout s'arrête | Le formulaire refuse proprement, **aucun lien WhatsApp fourni** — comportement déjà correct **[F]** |
| **Fournisseur d'envoi indisponible** | Messages en attente | Réessais ; **la demande n'est jamais perdue** **[F]** |
| **WordPress indisponible** | Site public et back-office | **Les consommateurs externes continuent de fonctionner** — propriété nouvelle de l'hybride |
| **Ordonnanceur arrêté** | File croissante, **silencieuse** | Battement + alerte (§9) |
| **Edge Function en échec** | Commandes externes refusées | Refus explicite, jamais silencieux |
| **Worker interrompu en cours** | Éléments bloqués « en cours » | Détection par âge, reprise après délai, contrôle de réconciliation |

La troisième ligne mérite d'être soulignée : dans l'architecture actuelle, une indisponibilité de WordPress arrête **tout**. Après la bascule, un chauffeur en mission continue de travailler. **C'est un bénéfice d'exploitation direct de l'ADR-001**, obtenu sans effort supplémentaire.

**Traitement partiel** : un lot interrompu ne laisse aucun élément dans un état ambigu — chaque élément porte son propre statut de livraison, et la reprise repart de l'état persisté (E7).

## 11. Déploiement progressif

Trois mécanismes, tous déjà disponibles ou décidés :

| Mécanisme | État |
|---|---|
| **Drapeaux de fonctionnalité** | La table existe avec trois valeurs, **mais aucun code ne la lit** **[F]**. C'est ici qu'elle prend enfin son sens |
| **Coexistence de workers** | Sûre par réservation atomique **[F]** — migration handler par handler |
| **Déploiement des policies** | Table par table, chacune testée indépendamment (ADR-004) |

Pas de déploiement canari : à cette échelle, **l'environnement de staging est le mécanisme de progressivité**.

### 11.1 Gouvernance des drapeaux de fonctionnalité

> **« Un drapeau de fonctionnalité active ou désactive une fonctionnalité. Il ne décide jamais d'une autorisation, d'un rôle, d'une règle métier, d'une policy RLS ni d'un niveau de sécurité. »**

Les décisions d'autorisation restent exclusivement dans l'ADR-004, les policies RLS, le domaine et le runtime.

**La distinction est pratique, pas théorique** : un drapeau désactivé doit rendre une fonctionnalité **absente**, jamais « présente mais interdite ». Si la seule chose qui empêche un accès est un drapeau, l'autorisation est manquante.

**Invariant E8.**

## 12. Séparation Production / Staging

Acquis : deux projets Supabase distincts, donc deux jeux de données et de secrets **[F]**.

**Manque vérifié, et c'est un risque d'exploitation réel** : `isProduction()` existe mais **n'est jamais appelé** ; `FCP_ENV` n'est lu que pour être affiché dans `/health` **[F]**. **Aucun garde-fou d'environnement ne protège les envois sortants.** Un staging correctement configuré pour l'envoi enverrait de vrais courriels à de vraies adresses — y compris lors d'une recette utilisant des données réalistes.

**Exigences** **[R]** :

1. **Garde-fou d'environnement sur toute communication sortante** — en dehors de la production, envoi bloqué ou restreint à une liste d'adresses autorisées ;
2. ordonnanceur et workers **propres à chaque environnement**, jamais partagés ;
3. secrets distincts par environnement — acquis **[F]** ;
4. **staging systématiquement avant production**, comme déjà pratiqué **[F]** ;
5. données de staging ne contenant pas de données personnelles réelles non nécessaires.

L'exigence 1 est la plus urgente : elle protège des personnes réelles, et son absence est aujourd'hui vérifiée.

### 12.1 Vérification automatique du garde-fou d'environnement

Le garde-fou est une **exigence vérifiable automatiquement**.

**Avant tout déploiement : un environnement non Production ne doit jamais pouvoir envoyer une communication réelle.**

Cette vérification sera intégrée aux tests d'exploitation (ADR-012 et ADR-015) et devient un **critère obligatoire avant mise en production**. Une exigence dont le respect dépend de la vigilance humaine finit par être violée ; celle-ci protège des personnes réelles.

**Invariant E9.**

## 14. Conséquences positives

L'asynchrone cesse de dépendre du trafic · la migration du worker est sûre grâce à une décision de conception antérieure **[F]** · quatre leviers de débit avant tout changement d'architecture · WordPress cesse d'être un point de défaillance unique pour les consommateurs externes · `pg_cron` retire à WordPress une tâche qui ne le concerne pas **[F]** · Q1 cesse d'être bloquante · les drapeaux de fonctionnalité trouvent enfin un usage **[F]**.

## 15. Conséquences négatives

Trois mécanismes de planification coexistent, à documenter · le battement d'ordonnanceur est un dispositif nouveau à construire · le garde-fou d'environnement modifie un comportement en production · deux workers en coexistence pendant les migrations demandent une vigilance temporaire · la voie de repli du §6 introduit une dépendance de Supabase vers WordPress, en sens inverse de l'architecture habituelle.

## 16. Risques

| Risque | Gravité | Atténuation |
|---|---|---|
| **Envoi réel depuis staging** | **Critique — vérifié** **[F]** | Garde-fou d'environnement, exigence 1, **E9** |
| Ordonnanceur arrêté sans alerte | **Critique** | Battement obligatoire (§9) |
| Rafale dépassant 240/heure **[F]** | Élevée | Leviers 1 et 2, mesurés avant d'agir |
| Handler bloqué « en cours » indéfiniment | Élevée | Détection par âge, reprise, réconciliation |
| Élévation injustifiée d'une Edge Function planifiée | Moyenne | A15, critères C1–C4 |
| Dépendance de repli Supabase → WordPress | Moyenne | Point d'entrée authentifié, à débit limité, journalisé |

## 17. Réversibilité

Cron système : réversible par retour à WP-Cron · `pg_cron` : réversible, la fonction reste appelable depuis PHP **[F]** · migration d'un handler vers une Edge Function : **réversible à tout moment**, les deux workers pouvant coexister **[F]** · battement : additif · garde-fou d'environnement : réversible par configuration · **aucune décision irréversible dans cette ADR**.

## 19. Conditions d'acceptation

1. Les responsabilités par runtime sont validées ; **le worker est un rôle, non un runtime**.
2. **Q-V est tranchée** : rôle assigné par handler ; WordPress en phase 1, Edge Function planifiée en phase 2, coexistence durable possible.
3. La coexistence de workers est reconnue comme **sûre par réservation atomique** **[F]**, ce qui rend la migration progressive et réversible.
4. La répartition de planification est validée : `pg_cron` pour la maintenance purement base · cron système ou repli Supabase pour la file · réveil immédiat conservé **comme optimisation, jamais comme garantie**.
5. **Il est acté que Q1 ne bloque plus l'Application Chauffeur** — un repli par planification Supabase existe.
6. **Aucune commande longue n'est synchrone.**
7. Les **quatre leviers de débit** sont validés comme préalables à tout changement d'architecture, le plafond actuel étant de **240 par heure** **[F]**.
8. **Le battement d'ordonnanceur est obligatoire**, son absence devant alerter.
9. **Un garde-fou d'environnement sur les communications sortantes est obligatoire** — l'absence actuelle est vérifiée **[F]** et constitue un risque pour des personnes réelles.
10. Les drapeaux de fonctionnalité deviennent le mécanisme de déploiement progressif, **usage qu'ils n'ont jamais eu jusqu'ici** **[F]**.
11. Q-Y et Q-Z sont renvoyées aux ADR-011 et 012.
12. **E6** validé — `pg_cron` est cantonné à la maintenance base ; la voie de repli du §6 relève d'une fonction planifiée applicative, non de `pg_cron`.
13. **E7** validé — les workers sont sans état ; la reprise repose exclusivement sur PostgreSQL.
14. **E8** validé — un drapeau désactivé rend une fonctionnalité absente, jamais « présente mais interdite ».
15. **E9** validé — le garde-fou d'environnement est **vérifiable automatiquement** et devient un critère obligatoire avant mise en production.
16. **E10** validé — déplacer un handler ne change jamais son comportement métier.

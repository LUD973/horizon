# ADR-006 — Contrat d'extensibilité

- **Numéro** : ADR-006
- **Titre** : Contrat d'extensibilité
- **Statut** : ACCEPTÉE
- **Corpus** : Architecture Horizon v1.0 — GELÉE
- **Référence** : v1.0.1 / d59409b8257f5a725828e281884a1c92e40da7a6
- **Date** : non consignée dans la source
- **Consolidation** : version finale produite à partir du texte initial et des ajustements validés

> **[F]** fait vérifié · **[R]** recommandation · **[H]** hypothèse

## 1. Statut

**ACCEPTÉE.** Dépend des ADR-001 à 005 (acceptées). Bloque l'ADR-007 et conditionne l'organisation des futurs modules.

## 2. Contexte et problème

Le dépôt **ne déclare aucun `apply_filters` ni `do_action`** **[F]**. Il n'existe donc aucune API d'extension : tout module additionnel doit modifier le code existant.

Ce n'est pas un défaut du Sprint 1 — avec un seul consommateur, un point d'extension n'aurait servi à rien. Cela devient structurant maintenant que six modules sont visés.

**Problème à résoudre** : permettre à un second consommateur d'exister sans modifier le cœur, sans transformer Horizon en framework générique, et sans qu'aucune extension ne puisse affaiblir la sécurité.

## 3. Objectifs et non-objectifs

**Objectifs** : permettre à un second consommateur d'exister sans modifier le cœur · empêcher le couplage direct entre futurs modules · garantir qu'aucune extension ne puisse affaiblir la sécurité · rendre les contrats testables et versionnés.

**Non-objectifs, explicitement** : Horizon n'est pas un framework générique · pas de catalogue de hooks « au cas où » · pas de place de marché d'extensions · pas de chargement dynamique de modules · **aucune exécution de code fourni par un utilisateur**.

**Règle de création** *(principe 2)* : **un point d'extension n'est introduit que lorsqu'un second consommateur réel ou planifié le justifie.** Cette ADR définit donc surtout des **règles**, et crée très peu de points.

## 4. Inventaire des points de greffe existants

| Point | Nature | Maturité |
|---|---|---|
| `SupabaseGateway` | **Interface PHP** | Solide — un double de test l'implémente déjà **[F]** |
| `CommunicationProvider`, `EmailProvider`, `ProviderResolver` | **Interfaces PHP** | Solides — conçues pour l'extension **[F]** |
| `ProviderRegistry` | Registre | Fonctionnel ; ajout d'un canal = une classe + un enregistrement **[F]** |
| `window.fcpConsent` — `hasConsent`, `onChange`, `openPreferences` | **Façade JS** | **La plus mature** — déjà consommée par un tiers interne **[F]** |
| `window.fcpAnalytics` — `track`, `trackOnce` | **Façade JS** | Mature **[F]** |
| Shortcode `[fcp_enquiry_form]` | Intégration contenu | Rendu non paramétrable **[F]** |
| Actions cron nommées ×3 + planification `fcp_5min` | Actions WordPress | Réutilisables telles quelles **[F]** |
| Namespace REST `fcp/v1` | Espace | Extensible par l'extérieur ; **aucun filtre sur l'existant** **[F]** |
| Capacité `fcp_horizon_access` | Contrôle d'accès WP | Réutilisable pour de futurs écrans **[F]** |
| Handles de scripts | Ordonnancement | Utilisables en dépendance **[F]** |
| Clés de configuration | Registre central | **Modification de code requise** — aucun filtre **[F]** |

**Constat** : le projet possède déjà **quatre interfaces PHP et deux façades JS** de bonne facture. L'extensibilité manquante n'est pas absente partout — elle manque là où le Sprint 1 n'avait qu'un consommateur.

## 5. Catégories de contrats d'extension — la décision structurante

**Trois niveaux, distingués par criticité.**

| Niveau | Mécanisme | Usage | Garantie | Portée |
|---|---|---|---|---|
| **1 — Contrat de domaine** | **Interface PHP typée** | Substitution d'un comportement critique | Typage, tests de contrat obligatoires | Intra-PHP |
| **2 — Événement métier** | Journal d'événements + handlers | Réaction à un fait, **découplage inter-modules** | Durable, rejouable, idempotent | **Inter-runtime** |
| **3 — Hook WordPress** | `apply_filters` / `do_action` | Adaptation locale **non critique** | **Aucune** — au mieux | Intra-WordPress |

**Règle de choix** *(principe 3)* : si le contrat est critique, c'est une interface. S'il s'agit de réagir à un fait, c'est un événement. S'il s'agit d'un ajustement local sans conséquence, c'est un hook.

**Principe transversal, applicable aux trois niveaux :**

> **« Une extension peut observer, enrichir, proposer ou transformer une représentation autorisée. Elle ne modifie jamais directement un agrégat métier critique en dehors des commandes prévues par le domaine. »**

Les modifications d'état métier passent **exclusivement** par : les commandes · les invariants · les règles d'autorisation · l'audit · les événements métier.

**Aucun hook ni aucune extension ne contourne cette règle.** Une extension qui écrirait directement un état métier échapperait simultanément à l'autorisation, à la qualification de sensibilité, à l'idempotence et à l'audit — c'est-à-dire à l'ensemble du dispositif construit par les ADR-002 à 005.

## 6. Interfaces PHP

**Décision** **[R]** : les interfaces existantes deviennent des **contrats déclarés**, avec un statut explicite. Une interface stable ne change pas de signature ; toute évolution passe par une nouvelle interface, l'ancienne étant dépréciée.

**Aucune interface nouvelle n'est créée par cette ADR.** `ProviderRegistry` couvre déjà l'ajout de WhatsApp, SMS et push **[F]** ; `SupabaseGateway` couvre déjà la substitution d'accès aux données **[F]**. Créer davantage aujourd'hui violerait le principe 2.

**Test de contrat** : toute implémentation d'une interface stable doit passer une suite commune. Un tel dispositif existe déjà de fait — le double de test de la passerelle de données **[F]** — et doit être formalisé.

### 6.1 Cycle de vie des interfaces

**Toute interface documentée porte un statut explicite.**

| Statut | Garantie | Peut être consommée |
|---|---|---|
| **Experimental** | Aucune — signature modifiable sans préavis | Interne uniquement |
| **Stable** | Signature figée ; seule une extension compatible est admise | Oui |
| **Deprecated** | Fonctionne encore ; remplacement désigné ; date de retrait annoncée | Migration en cours |
| **Removed** | N'existe plus | Non |

**Conditions de passage à Stable** : au moins **deux implémentations réelles** *(dont un double de test compte)* · documentation écrite · **suite de tests de contrat** que toute implémentation doit passer · aucune modification de signature depuis un cycle de livraison.

**Dépréciation** : annonce explicite · remplacement désigné · période de double disponibilité · **jamais de retrait sans passage préalable par Deprecated**.

**Compatibilité** : ajout d'une méthode optionnelle ou élargissement d'un type d'entrée = compatible. Retrait, restriction d'entrée, élargissement de sortie ou changement de sémantique = **nouvelle interface**.

Ce cycle est aligné sur les catégories A / B / C de l'ADR-005 : une évolution compatible relève de A, une rupture de B, une correction de sécurité de C.

**Statut des quatre interfaces existantes** : `SupabaseGateway` → **Stable** *(deux implémentations réelles* **[F]***)*. `CommunicationProvider`, `EmailProvider`, `ProviderResolver` → **Stable** *(implémentation Brevo + double de test* **[F]***)*.

## 7. Hooks et filtres WordPress

**Décision** **[R]** : les hooks sont autorisés **uniquement pour des adaptations locales non critiques**, et **interdits** sur les chemins de sécurité.

### 7.1 Zones interdites aux hooks

*Principe 5.* Aucun hook ne peut être placé sur :

| # | Zone |
|---|---|
| 1 | Résolution de l'acteur |
| 2 | Décision d'autorisation |
| 3 | Construction des prédicats de policy |
| 4 | Validation serveur — ni avant, ni après |
| 5 | **Écriture d'audit** — ni suppression, ni altération |
| 6 | **Qualification de sensibilité** d'une action |
| 7 | Vérification d'idempotence |
| 8 | Vérification de signature d'un webhook |
| 9 | Sélection d'un secret ou d'une configuration privilégiée |
| 10 | **Émission d'un événement métier** — un fait accompli ne se filtre pas |

**Zones autorisées** : libellés et présentation · rendu du formulaire *(la validation restant seule autoritaire)* · enrichissement du contenu d'une communication **avant rendu, sans changer le destinataire** · colonnes d'affichage au back-office · instrumentation et observabilité.

**Deux règles impératives :**

- **La valeur de retour d'un filtre est une entrée non fiable.** Elle est validée et normalisée comme n'importe quelle donnée externe. Un filtre qui renvoie un type inattendu ne doit jamais atteindre la couche de données.
- **Toute dépendance d'ordre d'exécution est explicite et testée.** Le code actuel en fournit le contre-exemple : l'ordre entre l'impression du chargeur de consentement et l'exécution des scripts repose sur une convention de priorité non contractuelle et non testée **[F]**.

### 7.2 Classification des hooks

**Aucun hook ne devient contractuel par accident. Le statut est explicite et déclaré à la création.**

| Niveau | Nom | Garantie | Documentation | Test |
|---|---|---|---|---|
| **1** | **Hook interne** | **Aucune** — modifiable librement | Non | Non |
| **2** | **Hook documenté** | Compatibilité raisonnable, sans engagement formel | Oui | Recommandé |
| **3** | **Hook contractuel** | Versionné, compatible selon la politique officielle | **Obligatoire** | **Obligatoire** |

Un hook non déclaré est de **niveau 1 par défaut**. La promotion vers le niveau 3 est une décision, jamais une conséquence de l'usage.

**Les dix zones interdites du §7.1 s'appliquent aux trois niveaux sans exception** : un hook interne n'a pas plus de droits qu'un hook contractuel sur les chemins de sécurité.

## 8. Événements métier et contrats inter-runtime

**Les événements métier ne sont pas des hooks WordPress** *(principe 6)*. La justification est technique, pas doctrinale :

| | Hook WordPress | Événement métier |
|---|---|---|
| Portée | Processus WordPress uniquement | **Tous les runtimes** |
| Durabilité | Aucune | **Persisté** |
| Rejouabilité | Aucune | **Rejouable** |
| Ordonnancement | Synchrone, dans la requête | Asynchrone, découplé |
| Échec | Peut casser la requête | **N'affecte pas l'écriture métier** |

Une Edge Function, un worker ou une passerelle IA **ne peuvent pas consommer un hook PHP**.

> **« Les événements métier constituent le principal mécanisme de découplage inter-runtime. Les commandes synchrones, les contrats API, les webhooks et les événements répondent à des besoins différents et constituent des contrats d'intégration complémentaires. »**

**Quatre contrats aux responsabilités distinctes :**

| | **Commande** | **Requête** | **Webhook** | **Événement métier** |
|---|---|---|---|---|
| Nature | Intention | Question | Notification entrante d'un tiers | **Fait accompli** |
| Temps | À l'impératif | Au présent | Passé, chez le tiers | **Au passé, immuable** |
| Peut échouer | **Oui** | Oui | *(déjà survenu)* | **Non — c'est déjà arrivé** |
| Destinataires | **Un** | Un | Nous | **Zéro à n** |
| Couplage | Fort, assumé | Fort, assumé | Imposé par le tiers | **Faible — l'émetteur ignore qui écoute** |
| Idempotence | **Clé obligatoire** | Naturelle | Identifiant fournisseur | Identifiant d'événement |

**Responsabilités distinctes** : la commande *fait faire* · la requête *interroge* · le webhook *informe depuis l'extérieur* · l'événement *constate*. Aucun ne remplace l'autre. Un module qui aurait besoin d'une réponse immédiate n'utilise pas un événement ; un module qui réagit à un fait n'appelle pas une commande.

**Ce que le découplage garantit** : deux modules ne s'appellent jamais directement pour réagir à un fait. Leurs interactions synchrones, lorsqu'elles sont nécessaires, passent par un **contrat API explicite**, jamais par un appel interne. L'ADR-007 précise leurs interactions.

**Conséquence directe pour la prévention du couplage** **[R]** : le module chauffeur ne connaît pas le module commercial ; il émet des faits, l'autre y réagit. La conception détaillée relève de l'ADR-007.

## 9. Extensions JavaScript

Les deux façades existantes sont **déjà des contrats publics de fait** **[F]** — le module d'analytique consomme celui du consentement.

**Décision** **[R]** : les déclarer comme contrats **versionnés et stables**, avec une garantie de compatibilité ascendante. Leur valeur est structurelle : elles permettent de conditionner n'importe quel script au consentement sans connaître le CMP, et d'émettre un événement sans connaître l'outil de mesure.

### 9.1 Gouvernance des façades

**Leur documentation fait partie du contrat.** Chaque façade déclare :

| Élément | Exigence |
|---|---|
| Version actuelle | Exposée et lisible par un consommateur |
| Compatibilité minimale | Version en deçà de laquelle le comportement n'est pas garanti |
| Politique de dépréciation | Méthode conservée puis retirée après annonce |
| Compatibilité ascendante | Garantie sur les méthodes de niveau contractuel |
| **Méthode absente** | Le consommateur doit pouvoir le détecter et **dégrader sans erreur** |
| **Configuration incomplète** | Comportement **sûr par défaut**, sans exception ni bruit |

Les deux dernières lignes formalisent un comportement déjà présent et correct : sans configuration, le CMP n'est jamais chargé et l'analytique n'injecte aucun script **[F]**. **Le comportement existe ; c'est le contrat qui manquait.**

**Réserve** : les façades sont aujourd'hui documentées par le code seul. Une façade sans contrat écrit est un contrat implicite — donc fragile.

## 10. Providers et intégrations externes

Le registre de fournisseurs de communication est **le point d'extension le mieux conçu du projet** **[F]** : ajouter un canal se fait par une classe et un enregistrement, sans toucher au domaine ni à l'application.

**Décision** : le conserver tel quel comme modèle de référence pour toute future intégration — paiement, messagerie, notification. **Le patron est validé ; il n'a pas besoin d'être remplacé.**

## 11. Sécurité des extensions

| Règle | Énoncé |
|---|---|
| S1 | **Aucune extension ne reçoit de secret.** |
| S2 | **Aucune extension ne reçoit `service_role`.** |
| S3 | La sortie d'une extension est une **entrée non fiable**. |
| S4 | **Une extension ne peut pas élever ses droits** : elle s'exécute après une autorisation déjà décidée. |
| S5 | **Aucun hook ne permet de neutraliser RLS, l'autorisation, l'audit ou la validation serveur** (§7.1). |
| S6 | Une extension ne peut pas modifier la qualification de sensibilité d'une action. |
| **S7** | **Une extension observe, enrichit, propose ou transforme une représentation autorisée — elle ne modifie jamais un agrégat critique hors des commandes du domaine** (§5). |

**Point d'honnêteté** : dans WordPress, **il n'existe aucune isolation entre extensions**. Un plugin tiers installé sur le site partage le processus PHP et peut déjà lire les constantes de configuration, donc `service_role` **[F]**. Ajouter des hooks **n'affaiblit donc pas la sécurité** — la surface existe déjà, entièrement.

**Conséquence** : la sécurité vis-à-vis des plugins tiers **ne relève pas de la conception des hooks**, mais de la gouvernance des plugins installés — inventaire, provenance, mises à jour, principe du moindre plugin. C'est un sujet pour les ADR-011 et 014, pas pour celle-ci. **Le dire évite de croire qu'un contrat d'extension bien conçu protège de quoi que ce soit sur ce plan.**

## 12. Gestion des erreurs d'une extension

*Principe 7 : une extension défaillante ne doit pas corrompre la transaction métier.*

| Niveau | Comportement en cas d'échec |
|---|---|
| **1 — Interface** | L'implémentation **est** l'opération : l'échec fait échouer l'opération, **en refus fermé**, jamais silencieusement |
| **2 — Événement** | **L'écriture métier est déjà validée.** Le handler échoue seul, est réessayé, puis mis en échec définitif. **Le fait n'est jamais perdu** |
| **3 — Hook** | Isolé, hors section transactionnelle. Une erreur ne doit ni annuler l'écriture, ni interrompre la chaîne |

Le niveau 2 possède **un précédent éprouvé en production** : un échec d'envoi de communication ne fait jamais perdre une demande **[F]**. Le mécanisme est validé, il est généralisé.

## 13. Versionnement et dépréciation

| Type | Versionnement | Dépréciation |
|---|---|---|
| Interface stable | Nouvelle interface pour toute rupture | Ancienne marquée, retirée après période annoncée |
| Événement métier | **Type d'événement versionné** | Ancien type consommé jusqu'à extinction |
| Hook | Version incluse dans le nom si la charge utile est contractuelle | Annonce puis retrait |
| Façade JS | Compatibilité ascendante garantie | Méthode dépréciée conservée puis retirée |

**Règle** : **un contrat non documenté n'est pas un contrat.** Un point d'extension livré sans documentation ni test est une dette, pas une fonctionnalité.

## 14. Tests de contrat

| Niveau | Test |
|---|---|
| Interface | Suite commune que toute implémentation doit passer |
| Événement | Conformité du schéma · **idempotence du handler** · rejouabilité |
| Hook | Présence · forme de la charge utile · **validation de la valeur de retour** · **ordre d'exécution lorsqu'il est contractuel** |
| Façade JS | Stabilité de la signature · comportement en l'absence de configuration |
| **Sécurité** | **Aucun hook sur une zone interdite** — vérification automatisable |

Le dernier test est le plus important : il transforme la règle du §7.1 en garantie mécanique plutôt qu'en discipline.

## 15. Impacts sur les futurs modules

| Module | Ce dont il dispose | Ce qu'il devra créer |
|---|---|---|
| CRM | Interfaces et capacité existantes | **Rien de nouveau** — consommateur unique |
| Chauffeur | Événements ; contrats API spécialisés | Événements du cycle opérationnel |
| Partenaire | Idem | Projection partenaire |
| Client | Idem | Projection client |
| Conciergerie | Registre de fournisseurs | **Paramétrage de verticale** — le formulaire est mono-vertical en dur **[F]** |
| IA | Passerelle, registre d'outils | Contrats d'outils versionnés |
| Paiement | **Patron du registre de fournisseurs** | Fournisseur de paiement + webhook |

**Sur la Conciergerie** : le domaine connaît déjà trois catégories de service **[F]** alors que la présentation n'en propose qu'une **[F]**. Le besoin d'extension est réel et planifié — mais **la réponse la plus simple est un paramètre du shortcode, pas un hook**. Appliquer le principe 3 : le mécanisme le plus simple qui suffit.

## 16. Invariants

**Famille G — Gouvernance de l'extensibilité**, créée par la présente ADR.

| # | Invariant | Domaine protégé |
|---|---|---|
| **G1** | Toute interface porte un statut : Experimental · Stable · Deprecated · Removed. | Cycle de vie des contrats de domaine (§6.1) |
| **G2** | Passage à Stable : deux implémentations réelles, documentation, suite de tests de contrat, signature figée depuis un cycle. | Qualité des contrats (§6.1) |
| **G3** | Aucun retrait sans passage préalable par Deprecated. | Compatibilité (§6.1, §13) |
| **G4** | Tout hook porte un niveau explicite ; **niveau 1 par défaut** ; la promotion est une décision. | Classification des hooks (§7.2) |
| **G5** | Les zones interdites s'appliquent aux trois niveaux de hook, sans exception. | Sécurité (§7.1, §7.2) |
| **G6** | Toute façade JS déclare version, compatibilité minimale, dépréciation, garanties, comportement en méthode absente et en configuration incomplète. | Contrats JavaScript (§9.1) |
| **G7** | Une extension observe, enrichit, propose ou transforme une représentation autorisée — **elle ne modifie jamais un agrégat critique hors des commandes du domaine**. | Intégrité métier (§5, §11 S7) |
| **G8** | Commande, requête, webhook et événement sont quatre contrats complémentaires aux responsabilités distinctes. | Contrats d'intégration (§8) |

**Invariants d'ADR antérieures appliqués** : **A16** (cohérence état / événement / attribution ; logs hors transaction) est présupposé par le niveau 2 du §12.

## 17. Conséquences positives

Les quatre interfaces et deux façades existantes sont valorisées plutôt que remplacées · les zones interdites rendent la règle de sécurité vérifiable automatiquement · l'événement devient le principal contrat inter-runtime, ce qui empêche structurellement le couplage direct entre modules · le patron d'isolation des échecs est déjà éprouvé en production **[F]** · **très peu de points nouveaux sont créés**, conformément au principe 2 · la distinction en trois niveaux donne une règle de choix nette.

## 18. Conséquences négatives

Trois mécanismes coexistent, à documenter · les événements imposent un coût de conception supérieur à un simple appel direct · les contrats versionnés créent une obligation de dépréciation qui n'existe pas encore dans le projet · les façades JS devront être documentées, ce qui n'est pas fait · une vérification automatisée des zones interdites reste à construire.

## 19. Risques

| Risque | Gravité | Atténuation |
|---|---|---|
| Hook placé sur un chemin de sécurité | **Critique** | Zones interdites §7.1 + test automatisé §14 |
| Valeur de retour d'un filtre non validée | Élevée | Règle S3, test de contrat |
| Couplage direct entre modules malgré tout | Élevée | L'événement comme principal contrat inter-runtime |
| Prolifération de hooks « au cas où » | Moyenne | Principe 2, non-objectifs §3 |
| Dépendance d'ordre implicite | Moyenne | Ordre explicite et testé — le précédent existe **[F]** |
| Illusion de protection vis-à-vis des plugins tiers | Moyenne | **§11 : la surface existe déjà ; le sujet est la gouvernance** |

## 20. Réversibilité

Retirer un hook non consommé : nul · retirer une façade JS : faible, un seul consommateur interne **[F]** · retirer une interface implémentée : moyen · **retirer un contrat d'événement consommé par un autre runtime : élevé** — c'est le seul engagement réellement durable, et c'est précisément pour cela qu'il doit être versionné.

## 22. Conditions d'acceptation

1. Les **trois niveaux** de contrat sont validés, avec leur règle de choix par criticité.
2. **Aucune interface nouvelle n'est créée** : les quatre existantes sont déclarées comme contrats, avec statut explicite.
3. Les **dix zones interdites aux hooks** sont validées comme contraignantes, et leur respect doit être **vérifiable automatiquement**.
4. La valeur de retour d'un filtre est traitée comme une **entrée non fiable**.
5. Toute dépendance d'ordre d'exécution est **explicite et testée**.
6. **Les événements sont le principal mécanisme de découplage inter-runtime, non le seul** ; commandes, contrats API et webhooks sont complémentaires, avec des responsabilités distinctes. Deux modules ne s'appellent jamais directement pour réagir à un fait.
7. Les deux façades JS sont déclarées **contrats publics versionnés**, à documenter.
8. Le registre de fournisseurs est validé comme **patron de référence** pour les intégrations futures, paiement compris.
9. Le comportement en cas d'échec est validé par niveau, le niveau 2 s'appuyant sur un patron déjà éprouvé en production **[F]**.
10. Il est acté qu'**un contrat non documenté n'est pas un contrat**.
11. Il est acté que **la conception des hooks ne protège pas des plugins WordPress tiers**, la surface existant déjà, et que ce sujet relève de la gouvernance des plugins (Q-U).
12. Le principe 2 est contraignant : **aucun point d'extension sans second consommateur réel ou planifié**.
13. Le **cycle de vie des interfaces en quatre statuts** est validé, avec ses conditions de passage à Stable et sa politique de dépréciation *(G1, G2, G3)*.
14. La **classification des hooks en trois niveaux** est validée, **le niveau 1 étant le défaut** et la promotion une décision explicite *(G4, G5)*.
15. La **gouvernance des façades JS en six points** est validée, leur documentation faisant partie du contrat *(G6)*.
16. Le principe **G7** est validé : aucune extension ne modifie un agrégat critique hors des commandes du domaine.

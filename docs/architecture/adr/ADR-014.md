## 2. Gestion des versions — résolution d'une ambiguïté existante

**Fait constaté à l'audit** **[F]** : trois références de version coexistent — jalon du dépôt `v1.0.1`, plugin `0.8.1`, thème `0.2.0` — **et rien ne vérifie leur cohérence**.

**Ce n'est pas une incohérence : c'est une convention non écrite.** Le jalon du dépôt marque une étape de programme ; les versions applicatives suivent leurs composants. Le lot v1.0.1 l'a explicitement établi — correction documentaire sans changement applicatif **[F]**.

**Décision : cinq portées de version, aucune version globale.** **[R]**

| Portée | Change quand | Exemple actuel |
|---|---|---|
| **Jalon de dépôt** | Livraison, étape de programme | `v1.0.1` **[F]** |
| **Plugin** | Changement applicatif du plugin | `0.8.1` **[F]** |
| **Thème** | Changement du thème | `0.2.0` **[F]** |
| **Contrat** | Rupture de contrat (ADR-005, 006) | — |
| **Edge Function** | Déploiement de la fonction | — |

**Une version globale unique serait un retour en arrière** : elle forcerait à incrémenter des composants inchangés et rendrait indéchiffrable ce qui a réellement évolué.

**Deux contrôles à automatiser** (transmis à l'ADR-015) : la version déclarée dans l'en-tête du plugin et la constante correspondante doivent concorder — elles concordent aujourd'hui **[F]**, mais **rien ne le vérifie** ; et le jalon doit énoncer les versions de composants qu'il embarque — ce que le journal des modifications fait déjà de fait **[F]**.

## 3. Stratégie de déploiement

**Ni bascule bleu-vert, ni déploiement canari.** À l'échelle de Q6, ce serait un surdimensionnement (principe 7). La stratégie est **staging puis production, dans un ordre strict**.

```
1. Migration d'EXTENSION        ← compatible avec le code encore en place
2. Déploiement du CODE          ← rollback toujours possible
3. ACTIVATION par drapeau       ← découple « déployé » de « actif »
4. OBSERVATION                  ← supervision quotidienne, ADR-013 §8
5. Migration de RÉDUCTION       ← livraison ultérieure, jamais la même
```

**L'étape 3 est la nouveauté et la clé** : elle sépare le moment où le code arrive du moment où la fonctionnalité agit. Sans elle, tout déploiement est une mise en service.

**L'étape 5 dans une livraison ultérieure** est ce qui garantit qu'à tout instant, la version précédente du code reste compatible avec le schéma en place.

### 3.1 Identifiant de déploiement

**« Chaque déploiement reçoit un identifiant unique. »**

Réutilisé dans : l'observabilité · les audits · les incidents · les rapports d'exploitation.

Il rejoint les identifiants de corrélation de l'ADR-012 §3 et suit **O1** — il ne change jamais de signification. Son intérêt est de répondre à la question la plus fréquente en incident : *« qu'est-ce qui a changé juste avant ? »*

**Invariant DPL3.**

### 3.2 Validation post-déploiement

**Le déploiement n'est pas terminé à la mise en ligne : il l'est à la validation.**

Tant que la validation n'est pas achevée : **la procédure de retour arrière reste immédiatement applicable** · la livraison est **en observation**.

Cela complète l'étape 4 ci-dessus : l'observation n'est pas une courtoisie post-livraison, c'est une **phase du déploiement**, pendant laquelle l'extinction d'un drapeau ou un redéploiement doivent rester à portée de main.

**Invariant DPL5.**

## 4. Migrations

Reprise de l'ADR-010 §15–16, sans ajout : registre par environnement (**D6**) · amorçage sans réexécution des cinq migrations existantes **[F]** · **sens unique**, corrections par migration compensatoire · empreinte divergente **bloquante** · RLS activée dans la migration qui crée la table · staging systématiquement d'abord **[F]**.

**Un seul ajout d'exploitation** **[R]** : une migration est **appliquée séparément du déploiement du code**, jamais dans le même geste. Les confondre rend impossible de revenir sur le code sans revenir sur le schéma — ce qui est précisément interdit.

## 5. Retour arrière

**Quatre objets, quatre stratégies distinctes :**

| Objet | Retour arrière | Délai |
|---|---|---|
| **Fonctionnalité** | **Extinction du drapeau** | **Immédiat, sans redéploiement** |
| Code WordPress | Redéploiement de la version précédente | Minutes |
| Edge Function | Redéploiement de sa version précédente, **indépendamment** | Minutes |
| **Schéma** | **Aucun** — migration compensatoire | Heures, réfléchi |

**Le retour arrière le plus rapide n'est pas un redéploiement : c'est l'extinction d'un drapeau.** C'est la justification opérationnelle des drapeaux, au-delà de l'activation progressive — et elle est plus importante que la première.

**Règle absolue** **[R]** : **le code doit toujours pouvoir revenir en arrière.** Toute livraison qui exigerait un schéma que la version précédente ne tolère pas est refusée — non parce qu'elle échouerait, mais parce qu'elle supprimerait l'issue de secours au moment où elle serait nécessaire.

## 6. Drapeaux de fonctionnalité — gouvernance

**État** **[F]** : la table existe avec trois valeurs à `false` ; **aucun code ne la lit**.

**Décision : les lire, avec un défaut sûr.** **[R]**

| Règle | Énoncé |
|---|---|
| **Défaut sûr** | Drapeau absent, illisible ou indéterminé ⇒ **désactivé** |
| **E8** | Un drapeau n'est **jamais** un mécanisme d'autorisation |
| **Absence, pas interdiction** | Un drapeau désactivé rend la fonctionnalité **absente**, jamais « présente mais interdite » |
| Portée | Par environnement |
| Lecture | En cache, avec durée courte — un drapeau doit s'éteindre vite |

**Chaque drapeau porte** : nom · **propriétaire** · finalité · date de création · **date de retrait prévue** · état par environnement.

**Distinction actée** **[R]** :

| | **Drapeau de déploiement** | **Option produit** |
|---|---|---|
| Finalité | Contrôler une mise en service | Configurer une offre |
| Durée de vie | **Temporaire — il doit mourir** | Permanente |
| Exemple | Activation d'un handler, d'une policy | `concierge_enabled` **[F]** |

**Un drapeau de déploiement sans date de retrait devient de la dette.** Les trois drapeaux actuels **[F]** relèvent en réalité de la seconde catégorie : ce sont des options produit, et il est légitime qu'ils soient permanents.

### 6.1 Gouvernance des drapeaux

Chaque drapeau porte : **propriétaire fonctionnel** · objectif · date de création · **type** *(déploiement ou option produit)* · **date prévue de retrait** lorsqu'il est temporaire · **justification documentée** s'il est conservé au-delà.

La dernière clause est celle qui empêche la dérive : un drapeau temporaire dépassant sa date n'est pas supprimé d'office — **il doit être justifié**, ce qui oblige à choisir entre le retirer et le reclasser en option produit.

**Invariant DPL2.**

## 7. Activation progressive — quatre axes

À cette échelle, la progressivité ne passe **jamais** par un partage de trafic. Quatre axes suffisent, tous déjà décidés ailleurs :

| Axe | Mécanisme | Origine |
|---|---|---|
| **Par environnement** | Staging puis production | ADR-013 §12 |
| **Par population** | Interne d'abord, externes ensuite | ADR-004 |
| **Par handler** | Bascule un par un, workers coexistants | **ADR-008 §4** **[F]** |
| **Par table** | Policies déployées une par une | ADR-004 §13 |

Aucun ne demande d'infrastructure de répartition. **Le troisième axe est sûr grâce à une décision de conception du Sprint 1** — la réservation atomique **[F]**.

## 8. Compatibilité ascendante — matrice

| Type de contrat | Compatible | **Incompatible — exige une version** |
|---|---|---|
| **Route publique** *(ADR-005)* | Durcissement de catégorie A | Catégories B et C |
| **Interface PHP** *(ADR-006)* | Méthode optionnelle, entrée élargie | Retrait, entrée restreinte, sortie élargie, sens changé |
| **Hook** | Charge utile enrichie | Retrait, changement de forme |
| **Façade JS** | Méthode ajoutée | Signature modifiée |
| **Événement** | Champ ajouté | Champ retiré, sens changé |
| **Schéma** | Colonne nullable, table, index | Retrait, renommage, resserrement |
| **Projection dédiée** | — | **Toute évolution ⇒ nouvelle relation** |

**Le cas le plus dangereux traverse toutes les lignes** : un **changement de sens à forme identique**. Aucun contrôle automatique ne le détecte. Il exige une **migration de contrat écrite** (ADR-010 §16).

## 9. Validation en staging et critères de passage en production

**Dix critères, tous vérifiables — c'est leur intérêt.**

| # | Critère | Origine |
|---|---|---|
| 1 | **Les tests ont réellement été exécutés** — pas silencieusement sautés | **Défaut vérifié** **[F]** |
| 2 | **Tests d'autorisation passés sur base réelle** | ADR-004 §14 |
| 3 | **Garde-fou d'environnement vérifié** | **E9** |
| 4 | Migrations appliquées en staging, registre cohérent | **D6** |
| 5 | Recette staging conforme | Pratique établie **[F]** |
| 6 | **Procédure de retour arrière identifiée pour cette livraison** | §5 |
| 7 | Drapeaux dans l'état attendu par environnement | §6 |
| 8 | Aucun secret introduit dans le dépôt | Analyse automatisée **[F]** |
| 9 | Si l'autorisation est touchée : **revue de policies** | ADR-004 |
| 10 | **Accord explicite du responsable de validation** | **Déjà documenté** **[F]** |

Le critère 10 existe déjà dans la checklist de déploiement **[F]** — il est repris sans modification. Le critère 1 corrige un défaut réel : une intégration continue verte ne prouve aujourd'hui pas que les tests ont tourné **[F]**.

## 10. Gouvernance des livraisons

**Une livraison est un ensemble de changements déployés ensemble, dont le périmètre est déclaré *avant*, non constaté après.**

| Élément | Décision |
|---|---|
| Périmètre | Déclaré à l'ouverture |
| Notes | Journal des modifications — **déjà bien tenu** **[F]** |
| Jalon | Marque du dépôt après validation |
| Traçabilité | Périmètre, tests, écarts, décision |

**Le lot v1.0.1 constitue un précédent utilisable tel quel** : périmètre annoncé et vérifié fichier par fichier, tests transmis, absence de changement applicatif démontrée par le diff, jalon posé après validation explicite, notes de version rédigées **[F]**. **La procédure existe déjà en pratique ; il reste à l'écrire.**

### 10.1 Manifeste de livraison

**« Toute livraison est accompagnée d'un manifeste de livraison versionné. »**

Contenu minimal : identifiant de livraison · **périmètre annoncé** · versions concernées · migrations incluses · **drapeaux concernés** · critères de validation · **procédure de retour arrière** · décision finale de validation.

Le manifeste est ce qui rend le §10 opposable : sans lui, « le périmètre est déclaré avant » reste une intention. **Le lot v1.0.1 en a produit un de fait** — périmètre des cinq fichiers, tests, absence de changement applicatif, commande de jalon, décision de validation **[F]** — sans qu'il porte ce nom.

**Invariant DPL1.**

## 11. Environnements et parité

Reprise de l'ADR-013 §12, avec **une exigence nouvelle** **[R]** :

**Parité entre staging et production** sur : version de PHP · extensions installées · forme de la configuration · capacités d'ordonnancement · présence d'un cache objet.

**Écart connu** **[F]** : la version de PHP réellement exécutée en production est **inconnue**, et l'intégration continue n'en teste qu'une seule. Un défaut propre à une autre version ne serait détecté qu'en production. **Cela relève de Q1 et de la matrice de versions à décider en ADR-015.**

### 11.1 Gouvernance des environnements

Chaque environnement porte : **un propriétaire** · un objectif · **un niveau de stabilité attendu** · une politique de mise à jour.

**La parité ne signifie pas identité absolue, mais cohérence documentée.** Un écart connu et justifié — un cache absent en local, un jeu de données réduit en staging — est acceptable ; un écart ignoré ne l'est pas. **Ce qui est interdit, c'est la divergence non documentée**, dont l'exemple actuel est la version de PHP en production, inconnue **[F]**.

**Invariant DPL4.**

## 12. Retour arrière des applications et des Edge Functions

| Runtime | Indépendance | Condition |
|---|---|---|
| WordPress | Redéploiement autonome | Ordre §3 respecté |
| **Edge Functions** | **Redéploiement autonome, par fonction** | **Contrats versionnés** |
| PWA *(futur)* | Version servie ; **attention aux clients hors ligne** | Tolérance de version côté serveur |

**La PWA introduit un cas particulier** : un client installé peut exécuter une version ancienne pendant des jours, et soumettre des commandes forgées par cette version. **Le serveur doit donc tolérer les versions récentes précédentes**, et non supposer que tous les clients sont à jour. C'est une contrainte propre aux applications installées, absente d'un site web.

## 16. Conséquences positives

L'ambiguïté des trois versions devient une convention écrite et vérifiable · l'ordre de déploiement garantit un retour arrière du code en toute circonstance · **le drapeau devient le retour arrière le plus rapide** · quatre axes de progressivité sans infrastructure · dix critères vérifiables plutôt qu'un jugement · **le précédent v1.0.1 fournit une procédure déjà éprouvée** **[F]** · le manifeste rend le périmètre opposable (**DPL1**) · l'identifiant de déploiement répond à « qu'est-ce qui a changé juste avant ? » (**DPL3**) · la parité devient une exigence de cohérence documentée, donc vérifiable (**DPL4**) · l'observation devient une phase du déploiement, pendant laquelle le retour arrière reste disponible (**DPL5**).

## 17. Conséquences négatives

La migration de réduction reportée à une livraison ultérieure allonge les changements structurants · les drapeaux exigent une gouvernance et un retrait discipliné · la parité d'environnements demande une vérification que rien n'assure aujourd'hui · la tolérance de version pour la PWA complique les contrats de commande · le manifeste est un artefact de plus à produire et à versionner · la validation post-déploiement prolonge la durée pendant laquelle une livraison reste en observation.

## 18. Risques

| Risque | Gravité | Atténuation |
|---|---|---|
| **Livraison exigeant un schéma non tolérable par la version précédente** | **Critique** | §5 — refus, pas une exception |
| **Intégration continue verte sans tests exécutés** **[F]** | **Critique** | Critère 1, ADR-015 |
| Drapeau devenu permanent par oubli | Moyenne | Date de retrait obligatoire · **DPL2** |
| Changement de sens à forme identique | Moyenne | Migration de contrat écrite |
| Client PWA ancien émettant des commandes | Moyenne | Tolérance de version serveur |
| Écart de version PHP staging/production **[F]** | Moyenne | Parité + matrice de versions · **DPL4** |
| **Livraison sans manifeste, périmètre constaté après** | Moyenne | §10.1 — **DPL1** |
| **Changement de comportement non rattachable à un déploiement** | Moyenne | §3.1 — **DPL3** |

## 19. Réversibilité

Toutes les décisions sont des pratiques, ajustables. **Aucune n'est irréversible** ; la seule contrainte durable est l'ordre de déploiement, qui existe précisément pour préserver la réversibilité de tout le reste.

1. **Cinq portées de version, aucune version globale** ; deux contrôles de cohérence à automatiser.
2. **Ni bleu-vert ni canari** ; ordre en cinq étapes, l'activation par drapeau découplant déploiement et mise en service.
3. **Une migration est appliquée séparément du déploiement du code.**
4. **Le code doit toujours pouvoir revenir en arrière** ; une livraison qui l'en empêcherait est refusée.
5. **Le drapeau est le retour arrière le plus rapide** ; défaut sûr : absent ou illisible ⇒ désactivé.
6. **Drapeau de déploiement** *(temporaire, avec date de retrait)* et **option produit** *(permanente)* sont distingués ; les trois drapeaux actuels **[F]** relèvent de la seconde catégorie.
7. **Quatre axes de progressivité**, aucun n'exigeant de partage de trafic.
8. La matrice de compatibilité est validée, le **changement de sens à forme identique** exigeant une migration de contrat écrite.
9. **Les dix critères de passage en production** sont validés, le critère 10 reprenant une pratique déjà documentée **[F]**.
10. **Le périmètre d'une livraison est déclaré avant**, et **le lot v1.0.1 sert de procédure de référence** **[F]**.
11. **La parité staging / production** est exigée, l'écart de version PHP étant reconnu **[F]** et renvoyé à Q-AK.
12. **Le serveur tolère les versions récentes précédentes de client PWA** (Q-AJ).
13. **DPL1** — manifeste versionné en huit points ; le lot v1.0.1 en fournit le précédent **[F]**.
14. **DPL2** — type, date de retrait et justification obligatoires ; un drapeau dépassant sa date doit être retiré ou reclassé.
15. **DPL3** — identifiant de déploiement propagé dans l'observabilité, les audits, les incidents et les rapports.
16. **DPL4** — propriétaire, objectif, stabilité et politique par environnement ; **cohérence documentée, non identité**.
17. **DPL5** — le déploiement s'achève à la validation ; retour arrière applicable pendant toute l'observation.
